# 成就系统统一设计方案

更新时间：2026-08-24

首期六款主推游戏的成就清单与产品范围，见[成就墙与解锁反馈体验设计](成就墙与解锁反馈体验设计.md)；成就墙的视觉线框、鸡窝勋章的动效与 ArkUI 原生实现选型，见[成就界面与游戏内提醒鸿蒙原生设计](成就界面与游戏内提醒鸿蒙原生设计.md)。勋章素材、页面视觉、合集里程碑和每款游戏的独立触发规则，统一从[成就系统文档索引](成就系统/文档索引.md)进入。

## 背景

当前成就功能集中在 `entry/src/main/ets/pages/HubPage.ets` 的 `Achievements()`：7 条成就条件直接写在 UI Builder 中，只能由最高分、收藏数和 `GameRecord.playCount` 推导。

这能展示最基础的“已完成/未完成”，但随着游戏增加会迅速失控：

- 成就定义、判定、展示耦合在一个页面，新增游戏必须修改大厅 UI。
- 分数不能代表所有玩法事实。例如“2048 高手”实际以总分达到 `2048` 判断，不能证明玩家合出了 `2048` 方块。
- 没有解锁时间、进度、去重、历史迁移或统一通知。
- 游戏页目前只通过 `recordScore(score)` 上报最终分数，扫雷胜利时间、空当接龙步数、2048 最大方块、俄罗斯方块消行数等信息都会丢失。
- `rps` 与 `rpsBattle` 的展示名称相同，若用名称而不是稳定 `gameId` 管理，成就会串到另一款游戏。

截至本文更新日，大厅实际可进入的游戏为 `rps`、`rpsBattle`、`freecell`、`minesweeper`、`chicken2048`、`tetris`、`suika`。`eggSling` 和 `whiteTiles` 已有游戏目录，但尚未在 `GameRegistry.ets` 与 `Index.ets` 中注册、路由；它们应按同一契约接入，不应为未上架游戏预埋大厅特例。

## 目标

- 所有已上架游戏使用同一套成就定义、事件、持久化、通知和展示规则。
- 游戏只上报真实玩法事实，合集壳统一决定是否达成成就。
- 新游戏可以在不改 `HubPage.ets` 判定代码的情况下接入。
- 成就可以显示进度、解锁时间和来源游戏，并支持浅色、深色与手机画布模式。
- 离线可用，不依赖账号、网络、排行榜或服务端。
- 历史用户升级后保留能够由现有记录可靠推导的成就，不凭猜测补发。

## 非目标

第一版不做以下内容：

- 金币、道具、皮肤、抽奖、付费奖励或每日任务。
- 账号登录、跨设备同步、云端防作弊、全球排行榜。
- 可编辑的成就配置后台或运行时下载的 JSON 规则。
- 按每一步操作记录完整事件日志。

这些能力会显著增加存储、迁移和作弊校验成本，当前离线小游戏合集不需要先承担它们。

## 统一原则

### 游戏上报事实，成就系统负责判定

游戏代码不得直接调用 `unlock('xxx')`。它只能报告“本局赢了”“最大方块为 1024”“消除了 4 行”“剩余 3 个鸡蛋”等事实；成就引擎根据固定注册表决定解锁项。

这样能避免游戏内散落成就 ID、同一事实重复领奖、名称改动导致失效，也使一条跨游戏成就不需要改每个游戏。

### 成就 ID 永远使用稳定键

格式统一为：

```text
global.<rule>
<gameId>.<rule>
```

示例：

```text
global.first_settlement
chicken2048.reach_2048
tetris.first_tetris
rpsBattle.supporter_wins
```

标题、描述、图标和阈值可以迭代，ID 一旦发布不能复用或改作别的含义。

### 先少而准，再扩展

每款游戏首批 2 到 4 条成就即可：一条入门、一条核心玩法、一条挑战或里程碑。成就不应只是把分数阈值换个名字，也不应在一局内连续弹出很多条。

## 用户体验设计

### 成就页

保留底部 Tab 的“成就”入口，内容从静态多行卡片改为可扫读的成就档案：

```text
成就墙                                      已解锁 8 / 30
████████████░░░░░░

[ 全部 ] [ 已解锁 ] [ 进行中 ]

合集里程碑
  图标  鸡窝开张                    已解锁 · 2026-07-25
  图标  常驻玩家                    12 / 50 局  ────────

鸡窝 2048
  logo  合成小能手                  最大方块 512 / 1024
  logo  2048 已达成                 已解锁 · 2026-07-25
```

布局规则：

- 标题行右侧只放紧凑的解锁计数，不做新的大横幅。
- 标题下用细进度条表达整体完成度；没有百分比大数字抢夺视觉层级。
- 使用原生 `Tabs` 或分段控件在“全部 / 已解锁 / 进行中”之间筛选；默认“全部”。
- 全局成就放在前面，游戏成就按 `GameRegistry` 的大厅顺序分组。游戏标题使用现有菜单 logo，避免重新绘制一套图标。
- 单条成就为一行轻卡片，不嵌套卡片：左侧 44-48vp 图标格，中间标题、条件和进度，右侧显示完成状态或解锁日期。
- 锁定项保留可读标题与达成条件，不用问号遮住内容；浅色下低饱和暖灰、深色下低对比暖灰即可。
- 有进度的条目显示 `当前 / 目标` 和细进度条；一次性成就显示“未达成”。
- 点击条目在底部半模态详情中显示完整条件、来源游戏、解锁日期和进度。详情只由用户主动打开，不在游玩中强制出现。

### 解锁通知

默认通知为顶部居中的非阻断成就胶囊，视觉上承接现有 `GameEntryBadge.ets`：

```text
  [游戏 logo / 星标]  新成就
                     合成小能手
                     最大方块达到 1024
```

规则：

- 普通成就在本局结算后展示 2.2 秒，不盖住底部控制区，不吞掉触摸事件。
- 关键里程碑可以即时展示，例如 `chicken2048.reach_2048`、`suika.final_merge`；必须在游戏自身合成/结算反馈之后入队，不能抢动画。
- 同一局解锁多项时一次只显示一条，其余进入队列；超过 3 条时合并为“本局解锁 3 项新成就”，详情留在成就页查看。
- 游戏进入身份胶囊可见时，成就通知等待它消失，避免顶部重叠。
- 当前声音与触感偏好尚未作为正式功能展示，第一版通知不擅自增加音效或震动；以后若这些设置真正启用，再由通知层统一读取。

### 鸿蒙原生实现选型

推荐使用应用根节点的 ArkUI 条件浮层，而不是系统 Toast 或模态自定义弹窗：

- 在 `Index.ets` 的现有根 `Stack` 中，条件挂载 `AchievementUnlockNotice`。它由 `@State` 驱动，并复用 `GameEntryBadge` 已验证的动画、定时器清理和 `HitTestMode.None` 模式。
- 动画使用 ArkUI `animateTo`、`transition`、`opacity` 和 `translate`，新增成就专用的 `CoopMotion` token。通知只表现状态变化，不负责判定或存储。
- `promptAction.showToast` 适合短文本即时反馈，但无法满足游戏 logo、进度、深浅色和队列控制，因此不作为主方案。
- `CustomDialog`、`bindSheet` 适合用户主动查看成就详情；它们会建立焦点/遮罩，不适合在操作中的游戏里作为每次解锁提示。
- 当前项目已由 `Index.ets` 持有 `snapshot` 并经 `@Prop` 下发。第一版继续沿用这条单向数据流，不为成就系统另起全局单例或迁移整站到 `AppStorage`。

HarmonyOS 官方的 ArkUI 状态管理、弹窗/Toast/Overlay 与 Preferences 文档应在实现时按项目实际 SDK 版本复核：

- [@State 装饰器：组件内状态](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V5/arkts-state-V5)
- [通过用户首选项实现数据持久化](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V5/data-persistence-by-preferences-V5)
- [ArkUI API 总览（含 CustomDialog、Toast、OverlayManager）](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V5/arkui-api-V5)

## 架构

```text
游戏 Page / Rules
  └─ 上报 GameSessionResult 或 GameAchievementEvent（事实）
        └─ Index.ets（应用级唯一入口）
              ├─ 更新最高分、局数、最近游玩
              ├─ AchievementEngine（纯判定）
              ├─ CoopStorage（一次写入完整 snapshot）
              └─ AchievementNoticeQueue（仅内存 UI 队列）
                    ├─ AchievementUnlockNotice（顶部非阻断提示）
                    └─ HubPage（成就墙、筛选、详情）
```

建议文件边界：

| 文件 | 职责 |
| --- | --- |
| `shell/AchievementModule.ets` | 成就、事件、进度、结算结果的稳定类型。 |
| `shell/AchievementRegistry.ets` | 静态成就目录、展示元信息、统一 ID 和规则声明。 |
| `shell/AchievementEngine.ets` | 纯函数：根据旧状态和事件计算进度、解锁结果，不依赖 ArkUI 或 preferences。 |
| `components/AchievementUnlockNotice.ets` | 可复用顶部通知 UI；第二个页面或游戏需要时才提升到全局组件。 |
| `pages/Index.ets` | 创建会话、接收事件、合并 snapshot、驱动通知队列。 |
| `pages/HubPage.ets` | 只渲染成就目录和 `snapshot.achievements`，不写判定阈值。 |
| `app/CoopStorage.ets` | 旧存档兼容、字段清洗、保存扩展后的 snapshot。 |
| `games/<gameId>/` | 组装当前局的事实；复杂计算仍留在对应 `Rules.ets`。 |

`AchievementRegistry` 使用 ArkTS 静态配置，不使用 rawfile JSON。配置与类型会在编译期校验，方便随代码、测试和版本迁移一起评审。

## 数据模型

下面是建议形态，字段名可以在实现时微调，但语义不要改变：

```ts
export interface AchievementMetric {
  key: string;
  value: number;
}

export interface GameSessionResult {
  eventId: string;
  sessionId: string;
  gameId: string;
  outcome: 'won' | 'lost' | 'finished' | 'abandoned';
  score: number;
  occurredAt: number;
  metrics: AchievementMetric[];
}

export interface GameAchievementEvent {
  eventId: string;
  sessionId: string;
  gameId: string;
  kind: 'milestone';
  occurredAt: number;
  metrics: AchievementMetric[];
}

export interface AchievementProgress {
  achievementId: string;
  current: number;
  unlockedAt: number;
  notifiedAt: number;
}
```

约束：

- `eventId` 由 `sessionId + 事件名 + 序号` 组成；引擎维护一个有上限的最近事件 ID 列表，重放同一事件不得重复累加。
- 不用 `Record<string, number>` 或任意 JSON 对象承载指标。使用稳定的 `AchievementMetric[]`，再由注册表白名单校验 `key`，更符合 ArkTS 的严格类型约束。
- 只保存进度、解锁时间和最近事件 ID；标题、描述、图标、规则全部来自静态目录。不要保存完整操作日志、Canvas 状态、图片或每局回放。
- `unlockedAt = 0` 表示未解锁。已解锁成就是单向状态，后续规则阈值调整不能把它重新锁住。
- `CoopAppSnapshot` 新增 `achievementSchemaVersion`、`achievements` 和有上限的 `recentAchievementEventIds`。旧 snapshot 缺失这些字段时默认空数组，不能影响已有最高分、收藏与主题。

`preferences` 当前适合保存这种小型本地状态；它会把首选项文件载入内存，因此事件历史必须严格限长。若未来需要大量局记录、跨设备同步或统计查询，再单独评估关系型数据库，而不是把整个成就日志塞进现有 `snapshot`。

## 规则模型

首版覆盖绝大多数需求的规则类型：

| 规则类型 | 示例 |
| --- | --- |
| 全局累计结算局数 | 完成 1 / 10 / 50 局。 |
| 全局已体验游戏数 | 在 3 / 7 个不同 `gameId` 中完成结算。 |
| 收藏数量 | 收藏 3 / 6 个上架游戏。 |
| 单局最高分 | 俄罗斯方块单局分数达到 1000。 |
| 单局指标最大值 | 2048 最大方块达到 1024；水果最高等级达到西瓜。 |
| 单局指标最小值 | 扫雷获胜用时不超过校准阈值；空当接龙步数不超过校准阈值。 |
| 单局布尔事实 | 扫雷胜利、空当接龙通关、最终水果合成。 |
| 累计事实次数 | 累计完成 10 次胜局、累计 20 次四消。 |

规则目录应优先声明式配置。只有无法由以上类型表达的复杂玩法，才在 `games/<gameId>/` 新建纯规则函数，并由 `AchievementEngine` 显式调用；不要在 UI Builder 或 Canvas 帧循环中临时判断。

## 当前游戏的首批候选成就

下表是接入目标，不代表所有阈值已经最终定稿。时间、步数和连击阈值应先从真机测试采集合理样本，再固化到注册表。

| 游戏 | 当前可稳定获得的事实 | 首批候选成就 |
| --- | --- | --- |
| `rps` | 结算胜者、各阵营数量、轮次、最高阵营分数。 | 完成首局；完成一场锦标赛；单局最高阵营数达到经校准阈值。 |
| `rpsBattle` | `winner`、`supportWon`、`elapsedSec`、`conversions`、`score`。 | 观战首胜；支持阵营获胜；单局转换数达到阈值。 |
| `freecell` | `won`、`moves`、`elapsed`、最终得分。 | 四花色归位；少步通关；限时通关。 |
| `minesweeper` | `win`、`elapsed`、胜利得分。 | 首次排雷成功；快速清场；连续获胜（需后续增加连续局统计）。 |
| `chicken2048` | `maxTile`、`movesMade`、`won`、分数。 | 合成 256；合成 1024；达成 2048。 |
| `tetris` | `score`、`lines`、`level`、`combo`、单次消行数。 | 首次四消；累计消除 20 行；达到等级 3 或更高。 |
| `suika` | `score`、`droppedCount`、`mergeLevel`、`isFinalMerge`。 | 今日瓜分 600；合成西瓜；最终水果合成。 |
| `eggSling`（待上架） | `levelClear`、`eggsLeft`、`score`。 | 过关；满鸡蛋过关；高分破坏。 |
| `whiteTiles`（待上架） | `score` / 已踩行数、失败结算。 | 连续踩过 30 行；连续踩过 100 行；刷新个人纪录。 |

特别说明：`chicken2048.reach_2048` 只能以 `maxTile >= 2048` 解锁，不能用分数代替。当前 2048 页面带有开发调试棋盘，调试入口必须标记为非正式会话，不能产生永久成就。

## 游戏接入契约

### 结算结果是必选接口

新增游戏接入时，将现有 `recordScore(score)` 逐步升级为：

```ts
recordGameResult: (result: GameSessionResult) => void = () => {};
```

最低要求是在正常结算、胜利或失败时只上报一次，包含 `score` 与该游戏注册表声明的指标。`Index.ets` 在同一次内存 snapshot 合并中更新最高分、局记录、成就进度和最近游玩，再统一调用一次保存。

迁移期保留 `recordScore(score)` 作为兼容桥：没有提供指标的旧游戏仍能更新历史最高分，但不能获得依赖玩法细节的新成就。每改一个游戏，再移除该游戏对旧接口的依赖。

### 即时里程碑是可选接口

只有必须在玩法发生时反馈的项目才调用：

```ts
reportAchievementEvent: (event: GameAchievementEvent) => void = () => {};
```

适用例子：2048 合成目标方块、鸡窝水果摊完成最终合成。普通“玩 10 局”“累计消 20 行”不应在每次操作时上报，统一放到本局结算计算。

### 新游戏接入清单

每个新游戏必须：

1. 在设计阶段列出可验证的结算事实，不用展示文案或临时 UI 状态作为成就依据。
2. 在 `AchievementRegistry` 添加 2 到 4 条定义，并使用唯一 `gameId` 前缀。
3. 在游戏 `Rules.ets` 或结算方法中构造指标，在页面层只负责转发。
4. 为每个新增规则补纯引擎测试：未达成、刚好达成、超过阈值、重复事件、旧存档迁移。
5. 在真机检查解锁提示不会挡住棋盘、控制区、结算按钮和系统手势区域。

禁止：

- 在游戏里直接写 `snapshot` 或 `preferences`。
- 每帧、每次碰撞或每次拖动都上报事件。
- 用本地化标题、图标文件名或数组下标作为成就身份。
- 调试按钮、开发棋盘、自动演示或测试脚本生成正式成就。

## 存档迁移

已有用户没有玩法细节历史，迁移只能使用现有 `records`、`favorites` 和 `recent` 做可信补发：

- 可以回填：首次结算、已体验游戏数、收藏数量、明确声明为“最高分达到 X”的成就。
- 需要谨慎回填：空当接龙通关。当前分数只在胜利时记录，实施时需以现有版本行为和测试确认后再决定。
- 不可回填：2048 达成目标方块、扫雷快速通关、最终水果合成、俄罗斯方块四消、弹射鸡蛋满鸡蛋过关。这些历史数据不存在，必须从升级后的新局开始统计。

回填产生的 `unlockedAt` 记录为迁移时间，成就详情显示“已由历史记录补发”，不能伪造原始达成日期。现有 7 条硬编码 UI 条件在迁移完成后删除，避免两套条件并存。

## 实施阶段

### 第一阶段：领域层与兼容迁移

- 新增 `AchievementModule`、`AchievementRegistry`、`AchievementEngine`。
- 扩展 `CoopAppSnapshot` 与 `CoopStorage.sanitize()`，保证旧存档可打开。
- 将 `HubPage.Achievements()` 的硬编码条件替换为只读目录和进度状态。
- 为全局成就、重复事件、旧存档回填补 ArkXTest / Hypium 纯规则测试。

### 第二阶段：优先游戏接入

优先接入事实已完整、用户可见度高的四款：`chicken2048`、`minesweeper`、`tetris`、`suika`。随后接入 `freecell`、`rpsBattle`、`rps`。

每个游戏单独提交，避免一个成就系统 PR 同时侵入所有游戏状态机。

### 第三阶段：展示与通知

- 实现成就墙筛选、进度、详情 sheet 和浅深色样式。
- 实现根 `Stack` 通知队列，与 `GameEntryBadge` 做时序避让。
- 真机验证 2048、扫雷、俄罗斯方块、鸡窝水果摊的解锁位置和触摸不受影响。

### 第四阶段：待上架与未来游戏

## 验收标准

构建与规则：

- `./scripts/build-app.sh --stacktrace` 通过。
- 成就引擎单元测试覆盖阈值边界、重复 `eventId`、非法 `gameId`、已解锁不回退、旧存档迁移。
- 同一局的最高分、游戏记录、成就进度只生成一次 snapshot 更新。

交互与视觉：

- 成就页不再包含硬编码业务条件，新增成就无需修改 `HubPage.ets` 判定逻辑。

- 顶部通知不阻断 Canvas、拖拽、按键和底部游戏控制；与进入身份胶囊不重叠。
- 多成就解锁按队列或汇总展示，不连续刷屏。
- 手机、小屏、折叠屏手机画布模式下无文字截断、底部 Tab 遮挡或控件重叠。

真机留档：

- 每个已接入游戏至少录一条“临界解锁”和一条“重复事件不重复解锁”的验证结果。
