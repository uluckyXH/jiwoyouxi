## 1. 结论

合集里程碑不是“默认赠送的成就”，而是跨游戏的真实进度：只由功能启用后收到的、一次且可信的事实事件推进。

本轮确认以下产品规则：

1. 只统计六款主推游戏：新版石头剪刀布大作战、空当接龙、扫雷、鸡窝 2048、俄罗斯方块、鸡窝水果摊。
2. “完成一局”指游戏自身产生了自然结果，不等于进入游戏、开始操作、主动返回大厅、重新开始或写入一次高分。
3. 一局只能推进一次全局局数；页面本地结算保护和引擎 `eventId` 去重同时生效。
4. 不读取旧 `GameRecord`、旧收藏或旧成就展示字段补发进度。成就功能启用前的历史数据保持原样，但不参与这套成就状态。
5. 收藏成就是应用壳事件，不伪装成游戏结算。它必须等收藏写入成功后再判定，并且不在大厅弹出游戏内成就提示。

当前已有静态定义、纯判定引擎、独立存储、成就墙和底部通知队列。六款主推游戏均已在指定自然结算出口上报事件，收藏家也已接入成功持久化后的应用事件；四条合集成就的代码路径均可达，尚待真机验收。

## 2. 当前实现审计

### 2.1 已落地的核心能力

| 能力 | 当前实现 | 结论 |
| --- | --- | --- |
| 成就目录 | `AchievementRegistry.ets` 中固定 22 条定义，包含 4 条 `global.*` | 展示目录已存在。 |
| 全局局数 | `AchievementState.completedSessionCount` 在六款主推游戏的有效 `sessionEnd` 时加一 | 引擎已实现，不读取旧战绩。 |
| 已体验游戏 | `AchievementState.playedGameIds` 按六款主推游戏的有效 `sessionEnd.gameId` 去重写入 | 引擎已实现，最多统计六款主推游戏。 |
| 去重 | 最近 32 个 `processedEventIds` 加页面自己的 `settled` / 已上报标记 | 重复回调不会重复累计或重复通知。 |
| 正式局过滤 | `isOfficial = false` 的事件直接被忽略 | 事件契约已实现。 |
| 独立存储 | `AchievementService` 通过 `CoopStorage` 单独读写 `achievement_state`，并串行化异步事件 | 不依赖大厅 `snapshot.records` / `favorites` 推导，连续事件不会相互覆盖。 |
| 收藏家事件 | `CoopStorage.save()` 返回 `Preferences.flush()` 结果，`Index.toggleFavorite()` 成功后才生成 `global` `milestone` | 失败恢复当前操作前快照，不上报事件。 |
| 通知 | `Index.ets` 将当前游戏首次解锁项放入队列，底部 ArkUI 胶囊逐张展示 | 全局收藏事件仅刷新状态，不打断大厅操作。 |

`AchievementEngine` 目前只接受已登记游戏档案中的 `sessionEnd` 或 `milestone` 事件。它先验证事件、过滤非正式局和重复事件，再更新全局计数、匹配已启用规则，最后写入事件 ID。

| --- | --- | --- | --- | --- | --- |

| `global.play_six_games` | 六边形鸡仔 | 启用 | 已实现 | 可达 | 六款主推游戏均已接入，种类按 `gameId` 去重。 |

### 2.3 已知但不能作为触发来源的旧路径

| 现有数据或调用 | 为什么不能用作合集成就真相 |
| --- | --- |
| `GameRecord.playCount` | 各游戏调用 `recordScore` 的边界不同：有的只在失败时调用，有的离开时也会调用，不能代表统一的正式结算。 |
| `GameRecord.highScore` | 是展示和最高分数据，不代表一局完整结果。 |
| `snapshot.favorites` | 只有当前值，无法证明哪次操作首次达到阈值，也不能安全补发历史成就。 |
| `achievementSummaryForSnapshot` 等兼容辅助函数 | 仅服务旧 snapshot 展示兼容；当前大厅和成就墙读取的是独立 `AchievementState`。 |

因此，不能通过“当前已有 10 局记录”或“现在已经收藏 3 个游戏”直接解锁合集成就。这样会违反当前成就核心的独立存档和不回填边界。

## 3. 最终成就定义

### 3.1 鸡窝开张

| 项目 | 设计 |
| --- | --- |
| ID | `global.first_settlement` |
| 条件 | 任一主推游戏首次产生有效正式 `sessionEnd`。胜利、失败、到时结束都可以；主动中断不可以。 |
| 进度 | `0 / 1`。 |
| 触发时机 | 游戏结果状态和既有结果层稳定后，由页面上报一次 `sessionEnd`。 |
| 通知 | 随当前游戏的底部成就队列显示。 |
| 当前状态 | 已由六款主推游戏的自然结算共同触发。 |

### 3.2 六边形鸡仔

| 项目 | 设计 |
| --- | --- |
| ID | `global.play_six_games` |
| 条件 | 六款主推游戏各自至少产生一次有效正式 `sessionEnd`。同一游戏重复结束不增加种类数。 |
| 进度 | 去重后的 `已体验 X / 6`。 |
| 触发时机 | 每个游戏自己的第一次正式结算；由引擎把 `event.gameId` 写入集合。 |
| 通知 | 第六款游戏结算的通知队列中显示。 |
| 当前状态 | 六款主推游戏均已接入；第六种不同 `gameId` 的正式结算解锁。 |

旧版 `rps`、尚未上架的 `eggSling`、`whiteTiles` 和将来新增游戏不纳入 `6` 的分母。若产品以后要调整主推游戏清单，必须写迁移方案，不能静默改变已发布成就的目标。

### 3.3 收藏家

| 项目 | 设计 |
| --- | --- |
| ID | `global.favorite_three` |
| 条件 | 用户通过大厅收藏操作，首次使有效主推游戏收藏数达到 `3`。 |
| 进度 | 当前事件证明的 `min(收藏数, 3)`；首次达到后永久解锁，之后取消收藏不回退。 |
| 触发时机 | 收藏新快照已成功 `Preferences.flush()` 后。取消收藏、写入失败、历史加载都不触发。 |
| 通知 | 不显示游戏内底部提示；成就墙与首页统计在状态刷新后更新即可。 |
| 当前状态 | 已启用；仅成功写入后的新增有效主推游戏收藏会生成事件。 |

收藏列表最多保存 12 个项目，但只有 `ACHIEVEMENT_PRIMARY_GAME_IDS` 中的六款才计入该成就。收藏旧版 `rps` 或未来的非主推游戏不会增加 `favoriteCount`。

### 3.4 常驻鸡仔

| 项目 | 设计 |
| --- | --- |
| ID | `global.complete_ten_sessions` |
| 条件 | 累计收到 10 个不同 `eventId` 的有效正式 `sessionEnd`。 |
| 进度 | `已完成 X / 10`，超过 10 后保持 `10 / 10`。 |
| 触发时机 | 每个游戏自然结果稳定后上报一次。 |
| 通知 | 第十个有效结算的当前游戏通知队列中显示。 |
| 当前状态 | 已由六款主推游戏的自然结算共同触发。 |

失败局可以计入“完成一局”，但前提是它确实进入了游戏的自然失败结果，而不是用户主动离开。这样既避免只有高手才能积累合集进度，也不会把“试了一下就退出”伪造成完整对局。

## 4. 正式结算与事件契约

### 4.1 统一定义

一条能推进合集进度的事件必须同时满足：

1. `gameId` 属于六款主推游戏。
2. `type = 'sessionEnd'`。
3. `isOfficial = true`。
4. 有稳定的 `sessionId` 与唯一 `eventId`。
5. 由游戏已有的自然结束函数产生，而非 UI 点击、路由离开、计时器清理或分数写入推导。

每次新开或重开正式一局时，页面生成一个新的 `sessionId`。同局结算事件固定使用：

```ts
eventId: `${sessionId}:session-end`
sessionId: sessionId
type: 'sessionEnd'
```

局内高光使用独立的事件后缀，例如 `${sessionId}:max-tile-256`；它们可用于游戏专属成就，但不增加全局完成局数。

### 4.2 明确不计入的情况

- 在设置页、倒计时、教程或未开始状态返回大厅。
- 点击重开、重新选择玩法或退出确认后离开当前局。
- 由开发工具、自动演示、摆盘、测试注入产生的结果。
- 同一结算函数被重复调用，或延迟上报计时器在重开/离开后又触发。
- 旧存档加载、首次安装时读取 `records`、收藏列表变更前的历史值。

游戏页面必须在 `aboutToDisappear`、重开和返回大厅时清理未执行的成就上报计时器。页面的 `settled` / `hasReportedAchievementSessionEnd` 是第一道保护；引擎的 `processedEventIds` 是第二道保护。

### 4.3 `recordScore` 与成就事件分离

`recordScore(score)` 继续只负责最高分、游玩记录和最近游戏。它不是成就结算接口，也不应被改造成大对象参数。

原因是当前各游戏调用它的条件不同：鸡窝 2048 会在带进度离开时记分，空当接龙只在通关时记分，俄罗斯方块、扫雷和水果摊则在各自的结束节点记分。合集成就只能旁路追加 `reportAchievementEvent(event)`，不能从 `recordScore` 反推结果。

| --- | --- | --- | --- | --- |
| 扫雷 | `MinesweeperPage.finish(won)` | 是 | 胜利和踩雷失败各一次。 | 当前 `settled` 与延迟上报已存在；保留已确认的看雷辅助局政策，不在合集改动中追溯修改。 |
| 石头剪刀布大作战 | `RpsBattlePage.finishGame(result)` | 是 | 仅正常完整对战结果各一次。 | `isInterventionMatch` 不计入；平局和零分正常局仍上报。 |
| 空当接龙 | `FreecellPage.checkWin()` | 是 | 当前只有通关属于自然结算。 | 游戏没有失败结果层；主动退出不计入，自动推进仍是正式玩法。 |
| 鸡窝 2048 | `Chicken2048Page.finishGame()` | 是 | 无可移动方块的失败结算各一次。 | 达到 2048 后允许继续游戏；开发摆盘标记为非正式局。 |
| 俄罗斯方块 | `TetrisPage.finishGame()` | 是 | Game Over 各一次。 | 暂停、退出确认和重开不计入；分数为 0 的自然结束仍应计入。 |
| 鸡窝水果摊 | `SuikaPage.finish()` | 是 | 溢出失败结果各一次。 | 投放水果后的主动退出不计入；600 分、西瓜、最终合成仍属于局内高光。 |

### 5.1 扫雷的既有例外

当前扫雷的成就设计已确认：开启看雷辅助后仍按正式局上报。这与其他游戏将来“开发摆盘必定非正式”的严格边界不同，但这是已发布行为，不能在接入合集时暗中改写。

若后续需要统一为“开发辅助不产生任何成就”，必须另起扫雷规则调整设计，明确对已有本地成就状态是否保留；本文件不负责追溯修改。

### 5.2 每款游戏最小改动模板

接入某款未接入游戏时，只允许做以下追加：

1. 在页面声明 `reportAchievementEvent: (event: AchievementEvent) => void` 回调。
2. 在开局/重开时建立 `sessionId`、正式局标记和结算已上报标记。
3. 在上表指定的稳定出口构造一个 `sessionEnd`。
4. 在 `Index.ets` 的该游戏路由处透传回调给 `reportAchievementEvent`。
5. 若该游戏已有专属高光成就，再在确认的规则出口追加 `milestone`；不得把判定放进 Canvas 主循环或 ArkUI `build()`。
6. 补 Hypium 规则测试、构建、真机验收和测试报告。

不改变现有玩法、不改变 `recordScore` 语义、不重排结算 UI，也不把成就通知组件直接导入游戏页。

## 6. 收藏家：应用事件设计

收藏家不能借用任何游戏的 `sessionEnd`，也不应在 `toggleFavorite()` 后直接根据内存数组解锁。目标实现分三步：

1. 扩展成就登记：为 `global` 增加只允许 `favoriteCount` 的应用事件档案；将 `global.favorite_three` 改为启用的 `eventFact` 规则，条件为 `favoriteCount >= 3`。
2. 让 `CoopStorage.save()` 或一个专用快照写入方法返回成功结果。`Index.toggleFavorite()` 先完成 Preferences 写入和 `flush()`，失败时恢复原快照且不报告成就事件。
3. 写入成功后构造一次全局 `milestone`：

```ts
{
  eventId: `favorites:${occurredAt}:${sequence}`,
  sessionId: `favorites:${occurredAt}:${sequence}`,
  gameId: 'global',
  type: 'milestone',
  occurredAt: occurredAt,
  isOfficial: true,
  facts: [{ key: 'favoriteCount', value: validFavoriteCount }]
}
```

`sequence` 用于避免同一毫秒连续操作产生相同 ID。事件处理后成就状态永久保持解锁；用户之后取消收藏不会回退。

当前 `Index.ets` 只在“事件的游戏 ID 等于正在游玩的游戏”时展示底部通知。`gameId = 'global'` 的收藏事件自然不会进入游戏内通知队列，符合“大厅收藏不打断操作”的要求。成就页重新进入时会刷新独立状态，因此无需为收藏成就增加额外弹窗。

## 7. 解锁展示和性能边界

### 7.1 游戏结算触发的合集成就

游戏页面应在既有结果层、清行/合成反馈或胜负动画稳定后才上报。扫雷现有延迟为 `350ms`，其他游戏在接入时应根据各自已有动效设置一个明确、可清理的延迟，不在帧循环中扫描或上报。

`Index.ets` 会把同一事件返回的 `newlyUnlocked` 转成队列：最多显示前三条独立提示，更多时显示汇总提示。全局成就与该局游戏专属成就可以同局解锁，但必须按同一队列串行显示，不能叠加遮挡结果页按钮。

### 7.2 大厅收藏触发的合集成就

收藏家只更新成就墙、首页勋章统计和详情状态，不展示底部游戏提示、不播放游戏音效、不触发震动。这样收藏按钮保持即时、安静，不让大厅操作被庆祝动画打断。

### 7.3 性能约束

- 结算事件每局最多一次；高光事件只在阈值首次跨越时产生。
- 成就状态读写只发生在事件时，不进入游戏主循环。
- 不在 ArkUI `build()` 中计算收藏进度、扫描游戏记录或生成事件 ID。
- 不引入 WebView、HTML、Node 运行时或跨端测试方案；保持 HarmonyOS 原生 ArkTS / ArkUI / Preferences 实现。

## 8. 实施顺序

### 阶段 0：设计校准（已完成）

- 重写旧草案中“历史回填”的内容，使其与当前独立成就状态一致。
- 明确四条全局成就的完成定义、事件来源、例外和通知策略。
- 不修改玩法或成就运行时代码。

### 阶段 1：让三个结算型合集成就在六款游戏中完整可达（已完成）

按风险从低到高逐款接入：

1. 新版石头剪刀布大作战：复用 `finishGame(result)`，排除干预赛。
2. 空当接龙：复用 `checkWin()`，只统计真实通关。
3. 鸡窝 2048：复用 `finishGame()`，把 2048 达成保留为局内高光。
4. 俄罗斯方块：复用 `finishGame()`。
5. 鸡窝水果摊：复用 `finish()`。

五款缺口游戏均已追加页面私有会话 ID、已上报标记与 `350ms` 可清理延迟。它们只在上述自然结果函数调用 `reportAchievementEvent(event)`，没有改写 `recordScore`、玩法主循环或结果 UI。

### 阶段 2：收藏家应用事件（已完成）

已实现收藏快照的串行写入、失败回退、`global` 仅允许 `milestone` 的事件档案与收藏家的 `eventFact` 规则。全局事件不会进入当前游戏通知队列。

### 阶段 3：真机校准与勋章资源（待执行）

- 按六款游戏各完成至少一局，确认全局局数和已体验种类准确。
- 用重开、退出、重复回调、开发工具路径验证不会误记局数。
- 确认同局多成就时底部提示不遮挡结果层和手势区域。
- 勋章 PNG 到位后只填写 `badgeAssetPath`，不改变规则 ID 和已解锁状态。

## 9. 测试与验收

后续实现必须遵守 [HarmonyOS 原生开发规范](../../鸿蒙原生开发规范.md)，使用 DevEco/Hvigor 构建和 HarmonyOS 官方 Hypium / ArkXTest。不得使用 Node 脚本替代 ArkTS 规则测试。

### 9.1 自动化测试

在 `entry/src/ohosTest/ets/test/` 增加或扩展以下 Hypium 用例：

| 用例 | 预期 |
| --- | --- |
| 首个正式 `sessionEnd` | 解锁鸡窝开张，局数为 1。 |
| 10 个不同正式结算 | 常驻鸡仔在第 10 局首次解锁，之后进度不超过 10。 |
| 同一 `eventId` 重放 | 局数、游戏种类和解锁项均不变化。 |
| 同一游戏多局 | 局数持续增加，但已体验游戏数只增加一次。 |
| 六个主推 `gameId` | 第六种游戏的结算时解锁六边形鸡仔。 |
| 非正式、退出或非法事件 | 不增加局数、不写去重 ID、不解锁。 |
| 平局 / 0 分自然结束 | 仍能作为正式结算计入合集进度。 |
| 收藏从 2 到 3 | 写入成功后仅解锁一次收藏家；取消收藏后不回退。 |
| 收藏写入失败 | 不生成收藏事件；页面保留操作前快照。 |

### 9.2 构建与真机验收

```bash
./scripts/build-app.sh --stacktrace
```

每次接入一款游戏时，真机至少验证：进入、开始、自然结算、重开、主动退出、返回大厅、成就页刷新、最高分原有行为和底部提示位置。涉及开发工具的游戏还要确认开发局不会按设计外的方式污染永久进度。

本轮构建与测试模块编译结果见根目录 `测试报告/2026-08-29-合集里程碑成就接入.md`。当前没有可用 `hdc` 目标，真机 Hypium 执行与流程验收保留到设备连接后完成。

## 10. 不做的事项

- 不从历史局数、收藏、最高分或旧 snapshot 成就字段回填。
- 不把旧版 `rps` 算作新版石头剪刀布大作战。
- 不把主动退出、重开或进入页面算作完成一局。
- 不为合集成就在游戏帧循环增加轮询、扫描或 ArkUI 状态更新。
- 不让收藏家在大厅显示会遮挡操作的游戏内弹窗。
- 不在本次全局方案中顺带调整任何游戏玩法、平衡、分数或结果页。

## 11. 完成定义

当且仅当下列条件全部满足时，合集里程碑接入才算完成：

1. 六款主推游戏都从各自指定的自然结果出口上报一次正式 `sessionEnd`。
2. 鸡窝开张、六边形鸡仔、常驻鸡仔都能在真实成就状态中按规则解锁。
3. 收藏家通过成功持久化后的应用事件解锁，且不回填历史收藏、不打断大厅操作。
4. 各游戏专属成就仍只由自身玩法事实判定，`recordScore` 与玩法结果保持原有语义。
5. Hypium 覆盖全局规则、重复事件和收藏写入失败；DevEco 构建通过。
6. 真机验收确认各结果层、底部提示、手势区、重开/退出流程及成就页刷新均正常。
