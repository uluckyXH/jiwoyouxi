# 成就模块核心架构设计

更新时间：2026-08-26
状态：阶段 A 已实现；核心尚未接通 `Index.ets`，未接入任何游戏，未实现游戏内提示

关联文档：

- [成就系统统一设计方案](../成就系统统一设计方案.md)：首期成就内容与产品范围。
- [成就墙与解锁反馈体验设计](../成就墙与解锁反馈体验设计.md)：成就墙和后续解锁反馈体验。
- [游戏成就设计模板](游戏成就设计模板.md)：每款新游戏确认玩法事实时使用。

## 1. 结论

成就系统应当是独立模块，游戏只是它的事实来源。

```text
游戏发生事实
    ↓ 仅上报通用事件
成就模块
    ├─ 静态成就目录与规则
    ├─ 进度、去重、解锁时间
    └─ 独立成就状态保存
    ↓
成就墙 / 后续游戏内提示
```

这套设计的关键不是把每个游戏改成同样的结构，而是让每个游戏只增加一个很小的出口：**报告事实，不判断成就。**

例如俄罗斯方块只说“本局单次消除了 4 行”，2048 只说“最大方块到了 256”。“这是否解锁第一记四消或合成小能手”完全由成就模块决定。

## 2. 本期范围：简单、独立、可扩展

### 要做

- 独立的成就状态、成就注册表和纯判定引擎。
- 一个通用的游戏事件上报入口。
- 进度、首次解锁时间和重复事件保护。
- 成就模块自己的全局统计，例如已完成局数、已体验游戏数。
- 只从功能启用之后收到的事件开始统计。
- 纯规则测试。

### 明确不做

- **不做旧存档可信迁移，也不补发历史成就。**
- 不读取或反推旧的 `GameRecord`、最高分、收藏、最近游玩来解锁成就。
- 不把现有 `recordScore(score)` 改成复杂的结果对象。
- 不改游戏玩法、页面布局、规则文件或 UI 结构。
- 不做服务端、账号同步、反作弊、完整事件日志。
- 不在核心模块阶段实现游戏内提示、音效、震动或结算页展示。

新版本启用成就后，所有玩家从一份空的成就状态开始积累。旧游戏记录仍按原样保留，但不参与成就计算；这比“猜测历史是否达成”更简单，也更诚实。

现有成就墙仍保留一条基于 `records`、`favorites` 的旧展示兼容路径，避免本阶段改变已上线页面行为；新核心状态保存于独立的 `achievement_state`，不会读取、改写或扩展那条旧路径。等阶段 B 明确接通应用壳和成就墙时，再单独替换展示数据来源。

## 3. 独立的含义

“独立”指职责和依赖独立，不要求为成就再造一套复杂的应用框架。

| 模块 | 可以知道什么 | 不能知道什么 |
| --- | --- | --- |
| 游戏 | 自己刚刚发生的玩法事实 | 成就 ID、阈值、存档、通知队列 |
| 成就模块 | 静态规则、成就进度、已处理事件 | 游戏 UI、Canvas、具体操作流程 |
| 应用壳 `Index.ets` | 如何把事件交给模块并保存状态 | 某条成就的判定细节 |
| 成就墙 | 当前成就状态和目录 | 游戏玩法事实、存储写入 |

因此，游戏中不能出现：

```ts
unlockAchievement('tetris.first_tetris')
```

游戏只调用：

```ts
reportAchievementEvent(event)
```

以后调整标题、勋章、阈值或新增一条同类成就，只修改注册表和测试，不需要回头修改已接入游戏。

## 4. 最小架构

```text
games/<gameId>/
  └─ reportAchievementEvent(事实事件)
          ↓
pages/Index.ets
  └─ AchievementService.report(event)
          ↓
shell/AchievementEngine.ets
  ├─ 校验事件
  ├─ 去重
  ├─ 匹配注册表规则
  └─ 返回新的 AchievementState + newlyUnlocked
          ↓
app/CoopStorage.ets
  └─ 只保存 AchievementState
          ↓
AchievementWall.ets
  └─ 只读显示进度
```

为保持简单，仍复用现有 `CoopStorage` 作为唯一 Preferences 写入入口；但成就状态以同一 Preferences 文件中的独立键 `achievement_state` 保存，引擎不读取 `records`、`favorites` 或游戏分数存档。独立不等于多建一个存储文件，关键是数据不互相推导、逻辑不互相依赖。

建议文件职责：

| 文件 | 职责 |
| --- | --- |
| `shell/AchievementModule.ets` | 成就、事件、状态和对外端口的稳定类型。 |
| `shell/AchievementRegistry.ets` | 游戏档案、成就目录、指标名与规则。 |
| `shell/AchievementEngine.ets` | 纯函数：输入旧状态和事件，输出新状态和首次解锁项。 |
| `app/AchievementService.ets` | 小型应用服务：持有当前成就状态，调用引擎并交给存储。 |
| `app/CoopStorage.ets` | 作为唯一 Preferences 入口，读取、清洗、保存独立键 `achievement_state`。 |
| `pages/Index.ets` | 把通用回调下发给游戏；不写规则。 |
| `pages/AchievementWall.ets` | 只读展示注册表和成就状态。 |

新核心的 `applyAchievementEvent`、状态初始化和状态清洗不得依赖 ArkUI、游戏页面、`preferences`、音频或通知组件；它们必须能脱离应用直接用单元测试运行。为保证本阶段不改变现有成就墙，`AchievementEngine.ets` 中暂时保留原有 snapshot 展示兼容辅助函数；该旧路径不参与事件判定或 `AchievementService` 的存储链路。

## 5. 一个统一事件就够了

第一版不区分多个复杂回调，游戏只使用一个事件类型。

```ts
export type AchievementEventType = 'sessionEnd' | 'milestone';

export interface AchievementFact {
  key: string;
  value: number;
}

export interface AchievementEvent {
  eventId: string;
  sessionId: string;
  gameId: string;
  type: AchievementEventType;
  occurredAt: number;
  isOfficial: boolean;
  facts: AchievementFact[];
}

export interface AchievementGateway {
  reportAchievementEvent: (event: AchievementEvent) => void;
}
```

约定：

- `sessionEnd`：一局正常结束时上报一次。胜负、分数、用时、步数等都放在 `facts`。
- `milestone`：只在需要立即记住的关键时刻上报，例如合成 256、四消、最终合成。
- 布尔事实统一使用 `0 / 1`，例如 `{ key: 'won', value: 1 }`。
- `sessionId` 每次新开或重开一局生成一次；`eventId` 由会话 ID、事件名和序号组成。
- `isOfficial = false` 的开发棋盘、看雷、自动演示或测试局可以上报用于观察，但引擎直接忽略，不产生永久进度。
- 游戏在自己的玩法反馈稳定后才上报里程碑；成就模块不干预动画或触摸流程。

示例：

```ts
{
  eventId: 'tetris-42:four-line-clear:1',
  sessionId: 'tetris-42',
  gameId: 'tetris',
  type: 'milestone',
  occurredAt: 0,
  isOfficial: true,
  facts: [
    { key: 'maxClearedLines', value: 4 },
    { key: 'totalLines', value: 12 },
    { key: 'level', value: 2 }
  ]
}
```

游戏不需要知道这些事实会命中几条成就。

## 6. 成就目录与规则

每款游戏在注册表拥有一个档案：它允许报告哪些事实、有哪些成就。新增游戏只新增自己的档案，不修改其他游戏。

```ts
export interface GameAchievementProfile {
  gameId: string;
  factKeys: string[];
  achievements: AchievementDefinition[];
}
```

第一版规则保持小集合，不设计通用脚本语言：

| 规则 | 表达方式 | 示例 |
| --- | --- | --- |
| 达到数值 | 某事实 `>= 目标` | 最大方块达到 256、单局消 20 行 |
| 等于事实 | 某事实 `= 目标` | 胜利标记为 1、最终合成标记为 1 |
| 小于等于 | 某事实 `<= 目标` | 胜利用时不超过校准值 |
| 多条件同时满足 | 两到三个事实都成立 | 胜利且支持阵营获胜 |

一条定义至少包含：

```ts
export interface AchievementDefinition {
  id: string;              // 例如 tetris.first_tetris，发布后不改
  gameId: string;
  title: string;
  summary: string;
  target: number;
  rule: AchievementRule;
  enabled: boolean;
}
```

规则阈值尚未确认时，保留成就文案但将 `enabled` 设为 `false`。不能因为展示在成就墙中就提前参与判定。

首期优先使用“一局达到一次即可解锁”的规则：进度由 `0 / 1` 或当前局最大值表达。需要长期累计的复杂成就，等真实需求出现后再单独设计，不预先引入事件日志或累计计数器。

## 7. 成就状态与进度控制

成就模块只保存自己的最小状态：

```ts
export interface AchievementProgress {
  achievementId: string;
  current: number;
  unlockedAt: number; // 0 表示未解锁
}

export interface AchievementState {
  version: number;
  progresses: AchievementProgress[];
  processedEventIds: string[];
  completedSessionCount: number;
  playedGameIds: string[];
}
```

说明：

- `progresses`：每条成就的当前进度和首次解锁时间。
- `processedEventIds`：保留最近固定数量的事件 ID，用来防止重复回调或崩溃后的立即重放。它不是完整事件日志。
- `completedSessionCount`、`playedGameIds`：由正式 `sessionEnd` 事件维护，供“完成首局”“累计完成十局”“体验六款游戏”等全局成就使用；不读取旧游戏记录。
- `version` 只用于未来数据格式兼容。旧数据缺失成就状态时直接创建空状态，**不做历史回填**。

“收藏三款游戏”这类不是游戏玩法事实的成就，不纳入第一版独立事件核心；现有目录可暂时保留展示，但应保持禁用。以后若确有价值，再为大厅操作单独设计应用事件，不能偷偷读取旧收藏数组补进游戏成就系统。

进度规则：

```text
nextCurrent = max(previousCurrent, 本次事件能证明的值)
nextCurrent 不超过 target

首次达到 target：写入 unlockedAt
之后永不回退、永不再次写入 unlockedAt
```

这样“最大方块 256”在之后又玩出 128 时仍保持解锁；重复上报同一个事件也不会重复改变状态。

## 8. 引擎处理流程

`AchievementEngine` 是一个纯函数：

```ts
applyAchievementEvent(
  previous: AchievementState,
  event: AchievementEvent
): AchievementApplyResult
```

返回：

```ts
export interface AchievementApplyResult {
  state: AchievementState;
  disposition: 'applied' | 'duplicate' | 'ignored';
  newlyUnlockedIds: string[];
}
```

处理顺序固定为：

1. 校验 `gameId`、事件类型、ID、数值和事实键。
2. 非正式局返回 `ignored`。
3. 已处理过同一 `eventId` 返回 `duplicate`。
4. `sessionEnd` 时更新模块自己的局数和已体验游戏集合。
5. 匹配该游戏和全局的已启用规则，按单向规则更新进度。
6. 收集本次从未解锁变为已解锁的 ID。
7. 将事件 ID 加入固定长度的去重列表，返回新状态。

应用壳只负责把新 `AchievementState` 保存到 `CoopStorage`。既有的 `recordScore(score)` 仍按原有路径处理，成就模块不读取它，也不干预它。

## 9. 与游戏的最小接入方式

核心模块完成后，每个游戏的改动只限于明确的事实发生处：

| 事实 | 游戏需要做的事 | 成就模块负责的事 |
| --- | --- | --- |
| 本局结束 | 上报一个 `sessionEnd` 事件 | 局数、全局进度、该游戏结算成就 |
| 达到 256 | 上报一个 `milestone` 事件 | 判断 256 / 1024 / 2048 等成就 |
| 单次四消 | 上报一个 `milestone` 事件 | 判断第一记四消 |
| 调试模式 | 标记当前事件 `isOfficial: false` | 忽略永久进度 |

不会要求：

- 拆分游戏页面；
- 将玩法状态机搬到成就模块；
- 修改既有分数、胜负、随机生成或物理逻辑；
- 把成就存档或通知组件导入游戏。

## 10. 新游戏如何加入

新增游戏时按以下顺序即可：

1. 确认稳定 `gameId`。
2. 写一份游戏成就设计文档，列出它能真实提供的事实。
3. 在注册表新增该游戏的事实键和 2～4 条成就定义。
4. 在该游戏一个明确的结算函数和必要的里程碑函数中上报事件。
5. 为规则补边界与重复事件测试。

除了第 4 步，不需要修改游戏代码；第 4 步也只是一条通用上报调用。没有可靠事实的成就先不做，不用分数、UI 文案或猜测代替。

## 11. 实施顺序

### 阶段 A：只完成独立核心（已完成）

只改成就模块、成就状态存储、测试和文档：

- 事件类型与 `AchievementGateway`。
- 静态注册表和少量规则类型。
- 纯判定、去重、正式局过滤、进度更新。
- 空状态初始化与单元测试。

此阶段禁止改 `games/**`、不接任何游戏、不做通知 UI、不改成就墙视觉。

本轮已落地事件类型、静态注册表、纯判定、去重、正式局过滤、独立存储服务和规则测试；没有修改 `games/**`、`Index.ets` 或成就墙 UI。

### 阶段 B：接通应用壳（待开始）

只在 `Index.ets` 增加一个通用事件接收入口，用测试事件验证保存和返回结果；仍不向任何游戏传递该入口。

### 阶段 C：逐个游戏接入

一次只选择一款游戏。开始前先确认“具体改哪个结算或里程碑函数”；实现后只验证这一款游戏，不做顺带重构。

### 阶段 D：后续提示

确认至少一个游戏接入稳定后，再独立设计并实现顶部成就提示。提示队列只消费 `newlyUnlockedIds`，不参与判定、不回写游戏状态。

## 12. 核心测试清单

- 空成就状态收到一个有效事件后能正确更新。
- 同一 `eventId` 再次提交不改变进度，也不再次返回解锁项。
- 非正式局不产生任何永久进度。
- 未达到、刚好达到、超过阈值都符合规则。
- 已解锁成就不会因后续较低数值回退。
- 未注册游戏、未知事实键、非法数值被忽略。
- 结算事件只更新模块自己的全局局数和已体验游戏集合，不读取历史游戏记录。
