## 1. 先纠正范围：当前只有一个正式棋盘

当前玩家实际可玩的扫雷只有默认棋盘：**`8 × 8`、`10` 枚鸡雷**。

代码中的 `normal`、`hard` 只是预留配置，不能作为当前成就条件：

- `MinesweeperPage` 始终以 `difficultyKey = 'easy'` 初始化；
- `MinesweeperHud` 的难度栏受 `showDifficultyBar` 控制，默认是 `false`；
- 页面没有传入 `showDifficultyBar`，所以玩家看不到、也无法选择中等或困难。

因此首批扫雷成就只基于这一个固定棋盘设计。下文的“入门 / 挑战 / 高难”是**成就门槛**，不是游戏难度选项。

## 2. 为什么仍建议扫雷做第一个

扫雷的一局结束边界已经非常清楚：`finish(won)` 有既有的 `settled` 防重入保护，胜负、用时和胜利结果层都已经存在。首个接入只需在这个单一出口补一条通用事实上报，不需要拆分页面、改棋盘算法或把通知组件导入游戏。

可稳定使用的玩法事实如下：

| 事实 | 当前代码来源 | 能否用于首批 | 说明 |
| --- | --- | --- | --- |
| 是否结算、是否胜利 | `MinesweeperPage.finish(won)` | 是 | 胜利、失败都可形成一次正式 `sessionEnd`；现有 `settled` 防止重复结算。 |
| 用时秒数 | `elapsed` | 是 | 首次翻格开始计时；暂停期间不累加。 |
| 固定棋盘规格 | `MinesweeperTypes.ets` 的默认 `easy` | 是 | 正式玩法固定为 `8×8 / 10 雷`，无需也不应上报难度等级。 |
| 胜利分数 | `minesweeperWinScore(elapsed)` | 能用但首批不用 | 分数完全由时间推导，不能当作第二套成就真相。 |
| 已翻安全格数 | `openedSafeCells()` | 能用但首批不用 | 胜利时一定等于安全格总数，区分度不足。 |
| 是否开启看雷开发功能 | `devRevealMines` | 是 | 当前作为快速验收辅助，开启后仍按正式局上报，不影响成就资格。 |
| 玩家插旗是否全对 | 只有当前 `MineCell.flag` | 是，本轮补两个小事实 | 胜利时系统会自动 `flagAllMines()`，不能从最终棋盘倒推玩家的真实插旗过程。 |

## 3. 首批三条成就（已确认）

| ID | 名称 | 成就门槛 | 精确条件 | 提示等级 | 勋章语义 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| `minesweeper.first_clear` | 平安出窝 | 入门 | 正式局胜利：`won = 1`。 | 普通 | 鸡蛋安全离开雷区 | 本轮启用。 |
| `minesweeper.quick_clear` | 迅捷排雷 | 挑战 | 正式局胜利，且 `elapsedSec <= 60`。 | 高光 | 时钟、闪电、小旗 | 本期固定为 `60` 秒并启用。 |
| `minesweeper.perfect_flags` | 旗开得胜 | 高难 | 正式局胜利；玩家在系统自动补旗前已手动正确插满全部 `10` 面旗，且本局从未在非雷格插旗。 | 高光 | 十面小旗围住鸡雷 | 本轮补齐事实上报并启用。 |

这三条分别对应三种不同体验：

- **完成感**：先让第一次赢的玩家有一枚明确勋章；
- **速度感**：在同一张固定棋盘上压缩用时，规则好理解；
- **策略感**：不是只靠“翻开所有安全格”，还要准确管理十面旗。

### 3.1 为什么固定为 60 秒

默认棋盘是 `8×8 / 10 雷`。`60 秒` 对熟悉基本推理的玩家是一个明确但并非极限的挑战；它比“只要通关”有压力，也不会因为没有多难度而要求特别长的时限。

本期先固定为 `60 秒`，并将“迅捷排雷”启用。后续应在真机记录至少 10 局正常玩法样本；若有足够证据需要调整，必须同时更新设计文档、注册表和测试，不在小版本中静默改变门槛：

- 若大多数熟练通关都在 `45 秒` 内，可将阈值收紧到 `45 秒`；
- 若稳定通关普遍超过 `75 秒`，可放宽到 `75–90 秒`；

### 3.2 同一局解锁多项时：严格依次提醒（已确认）

一局中命中两项或三项成就时，**所有成就都会提醒，但永远只显示一张通知卡**。前一张完整淡出并从根层卸载后，才挂载下一张；不并排、不叠卡、不抢同一帧。

首局正式胜利是预期的验证场景：

```text
本局首次正式扫雷胜利
  -> 解锁「鸡窝开张」（合集）
  -> 解锁「平安出窝」（扫雷）
  -> 先完整播放「鸡窝开张」
  -> 卡片卸载
  -> 再完整播放「平安出窝」
```

顺序规则：

- 成就引擎返回的 `newlyUnlocked` 顺序即通知入队顺序；通知数据转换和根层队列均不得排序、倒序或合并两条普通通知。
- 每条完整经历 `180ms` 入场、普通 `1.5s` / 高光 `1.8s` 停留、`180ms` 出场；上一条卸载完成前，下一条不能挂载。
- 一批最多逐条播放 3 条；第 4 条及之后只生成一条汇总提醒，排在前三条之后。
- 游戏重开、离开大厅或应用页面销毁时清空未播放通知；成就进度已经独立保存，但不会在之后补播历史弹窗。

测试要求：成就侧纯逻辑必须覆盖两条输入时的原始顺序，例如 `[global.first_settlement, minesweeper.first_clear]` 输出同一顺序；真机接入时再确认两张卡没有视觉重叠。

## 4. “旗开得胜”怎样做才可信

它不能读取胜利后的最终 `cells`，因为当前胜利流程会调用 `flagAllMines()` 自动插满旗。正确的实现应在**自动补旗之前**记录玩家行为。

后续只增加以下最小事实：

| 事实 | 含义 |
| --- | --- |
| `manualAllMinesFlagged` | 胜利前，十枚真实鸡雷都已经处于玩家手动插旗状态。 |
| `hasEverFlaggedNonMine` | 本局是否曾主动给非雷格插旗；即使后来撤销也保持 `true`。 |

成就条件为：`won = 1`、`manualAllMinesFlagged = 1`、`hasEverFlaggedNonMine = 0`。

这样能避免两个漏洞：

- 不插旗、只翻格通关，不能拿到“旗开得胜”；
- 曾经插错后再撤销，不能伪装成全程无误。

这只会在玩家主动切换旗帜时记两个轻量状态，不改变旗帜上限、自动补旗、棋盘随机或现有操作手感。

## 5. 正式局和上报边界

### 5.1 正式局

- 每次 `restart()` 生成新的 `sessionId`；当前扫雷的结算事件统一以 `isOfficial = true` 上报。
- 为方便验收，开启 `devRevealMines` 后继续按正常局判定；DEV 看雷只帮助定位鸡雷，不改变三条成就的规则。
- `finish(won)` 只上报一次，继续依赖现有 `settled` 作为最后防重保护。
- 未开始就返回大厅、确认退出、重开时被放弃的旧局不报告结算事件。

正常结算只需要上报游戏事实，不写成就 ID：

```ts
{
  type: 'sessionEnd',
  gameId: 'minesweeper',
  isOfficial: true,
  facts: [
    { key: 'won', value: won ? 1 : 0 },
    { key: 'elapsedSec', value: elapsed },
    { key: 'manualAllMinesFlagged', value: manualAllMinesFlagged ? 1 : 0 },
    { key: 'hasEverFlaggedNonMine', value: hasEverFlaggedNonMine ? 1 : 0 }
  ]
}
```

失败局同样可以上报一次正式 `sessionEnd`，供合集“完成任意一局”等成就统计；三条扫雷专属成就都要求 `won = 1`，所以失败不会解锁它们。

### 5.2 游戏内提醒时机

```text
MinesweeperPage.finish(won)
  -> 先显示既有胜利结果层
  -> 结果层入场稳定后（`350ms`）报告 sessionEnd
  -> AchievementService 判定并保存
  -> Index 根层队列展示 AchievementUnlockNotice
```

扫雷只负责上报事实，不能直接创建或关闭通知组件。报告通过 `CoopMotion.achievementResultReportDelay` 延后 `350ms`，避免顶部提示和既有弹层争抢第一帧；报告计时器必须在重开、退出和 `aboutToDisappear` 时清理。

暂停期间现有 `elapsed` 不计时。首批建议允许暂停后仍可获得“迅捷排雷”，保持玩家对当前计时器规则的既有理解；如果将来需要严格竞速，再单独设计“不暂停通关”成就，不在首批暗改规则。

## 6. 实施边界：现有扫雷代码保持玩法冻结

本轮已收到“开始接入扫雷”的明确授权；硬边界如下：

- `entry/src/main/ets/games/minesweeper/**` 只允许增加与成就事实上报直接相关的少量代码；不得改写、删除、重排既有游戏行为。
- 禁止擅自拆分 `MinesweeperPage.ets`，禁止移动、重命名或格式化既有游戏文件，禁止顺手调整棋盘算法、HUD、结果页、插旗规则、计时或 `recordScore`。
- 成就规则、通知队列、保存、展示数据转换和测试优先放在成就模块目录；游戏页不导入通知组件，也不判定成就 ID。

扫雷要提供真实事实时，唯一例外是已有结算出口旁的**追加式成就上报接缝**：只增加回调、会话 / 正式局标记、插旗事实和一次上报调用，不改动原来的结算、分数、UI 或玩法代码。每一处新增都必须能在 diff 中明确标为成就触发用途；任何超出此范围的游戏改动都要先重新征得确认。

## 8. 已确认项

已确认：

- 同局多项成就严格依次弹出；
- 当前只按默认 `8×8 / 10 雷` 正式棋盘设计；
- 首批固定为：**平安出窝 / 迅捷排雷（60 秒内）/ 旗开得胜（十旗全对）**；
- “迅捷排雷”允许暂停，沿用当前“暂停不计时”的既有规则；
- 不对现有扫雷代码做重构、拆分或非成就相关改动。

实现完成后，仍需按第 7 节的真机清单验收；自动化构建和成就纯逻辑测试不能替代该步骤。
