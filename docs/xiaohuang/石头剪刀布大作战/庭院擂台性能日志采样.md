# 庭院擂台性能日志采样

更新：2026-09-18，日志版本 v4。入口是首页“新版 · 庭院擂台”。

## 怎么复制

1. 重新 Run 新代码，在 DevEco Studio 打开 **HiLog**，选择正在运行游戏的设备和应用进程，搜索 **CoopArenaPerf**。
2. 开始一局，在“自定义人数与庭院事件”里可以直接选 **24 位 / 36 位 / 60 位**。先试平静庭院，再用相同模式和人数试事件。
3. 正常玩 20–30 秒，或玩到结算；复制连续日志，保留开始时的配置和卡顿前后内容。暂停或结算也会输出不足 5 秒的最后一段。
4. 一并说明体感发生在什么时刻，例如“60 位相遇时停一下”或“风场出现后持续变慢”。模式、人数、窗口、主题等大部分信息已自动记录。

不要只复制 FPS 那一个数字，也不要只留平均值。每 5 秒的三行属于同一组，使用相同的“局”和“段”编号：

- **采样开始 v4**：模式 / 挑战关卡、实际事件组合、随机种子、我方身份、初始三队人数、窗口与画布大小、像素密度、折叠状态、深浅色、效果和音效设置。
- **5秒汇总 v4**：人数范围、回调 FPS、P95 / 最长间隔、慢帧数、逻辑 / 绘制提交 / 总回调的平均与峰值、逻辑摊销 / 步、回调外间隙峰值。
- **模拟拆分 v4**：抽样步数；建网格、寻敌、移动、碰撞、事件与技能计分的每步平均；候选配对、实际接触、局部密度和补步负担。
- **场景负载 v4**：当前三队人数、累计转阵数、最密网格人数、可见特效峰值、UI 更新次数、UI / 音效提交时间、存档提交和实际完成时间。
- **停顿详情 v4**：较大的停顿单独记录，最多每两秒一条；超过 500 ms 自动暂停的情况另有“长停顿 v4”。
- **存档完成 v4**：异步保存耗时至少 100 ms 或失败时输出；完成时间包含排队，不能把它当成主线程阻塞时间。
- **素材 v2**：素材模块自身的版本标记；如有加载或绘制回退，连同 v4 的性能行一起保留。

## 怎么对比

先比较同一设备、模式、事件、主题、窗口大小下的 24 与 60 位队员。再单独改变一个条件，例如关闭音效、切到轻量效果或改变事件。每次改变主题 / 效果 / 窗口都会结束旧采样段并输出新场景信息。

| 观察到的变化 | 下一步重点检查 |
| --- | --- |
| 逻辑耗时随人数或最密格人数明显增长 | 看模拟拆分中的寻敌、碰撞或事件 / 技能是否增长 |
| 候选配对多，但实际接触很少 | 检查邻近筛选和网格范围 |
| 绘制提交增加，或 SVG 就绪数量不足 3 | 检查素材回退、图章与动态效果的绘制成本 |
| UI 更新次数和 UI 提交峰值增加 | 检查信息刷新、布局和绑定 |
| 总回调很短，回调间隔仍然很长 | 进一步检查设备调度、渲染呈现与模拟器负载，不能单凭日志归因 |
| 保存完成很慢，提交很短 | 先检查异步存储排队；它本身不证明游戏线程阻塞 |

模拟拆分约每 11 次回调采样一次；不在每个队员或每次碰撞中读取时间 / 打印日志。这个周期也避免总是采到相同的 AI 更新相位。日志里的“抽样每步平均”和“每回调平均”分母不同，不能直接相加。“逻辑摊销 / 步”用全部逻辑耗时除以实际模拟步数，包含固定调度开销；可与“步 / 回调”一起观察连续补步是否放大了卡顿。

**回调 FPS 和 Canvas 绘制提交时间都不等于 GPU 实际呈现帧率或 GPU 绘制时间。** 当前没有宣称实机满帧；收到连续实测日志后，再据此选择优化点。

60 位快速乱斗有可能很快清场，结算日志同样有效，不需要凑满五秒。要观察持续的多人、技能和事件负载，可再用 60 位“据点争夺”玩一局；比较时分别保留模式标签。
