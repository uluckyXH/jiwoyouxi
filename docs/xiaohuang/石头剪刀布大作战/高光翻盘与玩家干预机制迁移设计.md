# 石头剪刀布大作战高光翻盘与玩家干预机制迁移设计

日期：2026-08-24
状态：已实现，待 HarmonyOS 真机验收
适用范围：新版 `entry/src/main/ets/games/rpsBattle/`

## 1. 背景与目标

新版已经完成四种模式的手机端适配：经典乱斗、团队占点、小心叛徒、众生平等。旧版仍有三项未迁移能力：`悬赏头名`、`我要打十个`、`上帝之手`。

三者的定位并不相同：

| 机制 | 旧版作用 | 新版定位 |
| --- | --- | --- |
| 悬赏头名 | 持续抑制人数优势，奖励围剿头名 | 轻量反滚雪球规则 |
| 我要打十个 | 极端劣势时制造一次高光反杀 | 重量级翻盘事件 |
| 上帝之手 | 玩家触摸战场推开或吸引单位 | 明确标记的手动干预玩法 |

目标不是把三个旧开关塞回现有模式卡，而是在不破坏四种模式身份、手机端可读性和性能边界的前提下，提供可理解、可控、可测试的增强选择。

## 2. 核心结论

### 2.1 新增独立的“战局强化”卡

在现有纵向配置流中新增一张游戏私有配置卡，位于“本局机制”之后、“阵营主题”之前：

```text
01 玩法方案
02 本局机制
03 战局强化
04 阵营主题
05 支持阵营
06 战斗规模
07 对局时长
```

它不是全局规则库，也不展示当前模式不支持的反滚雪球规则。`上帝之手`作为跨模式的手动干预项始终可选；`悬赏头名` 和 `我要打十个` 仅在经典乱斗中出现。这样其他三种模式仍能提供可控的手动参与，但不会被不适配的翻盘规则打断。

### 2.2 悬赏头名与我要打十个必须互斥

两者都是“反滚雪球”规则，不能同时启用：

- 悬赏头名会持续压制领先方，使十倍人数差通常无法形成。
- 我要打十个在极端人数差出现后反转碰撞结果；再叠加悬赏的追击偏置、护盾和加速，会让结果难以理解和调参。
- 两个事件同时出现时，玩家无法判断本局是因持续围剿还是因英雄反杀而翻盘。

因此 UI 使用单选分段控件，而不是两个独立开关：

```text
反滚雪球
[关闭] [悬赏头名] [我要打十个]
```

### 2.3 上帝之手独立于反滚雪球规则

上帝之手不改变阵营克制，但允许玩家实时改变站位，属于“手动干预局”，不是自动事件。它应适用于新版全部四种模式，而不是只服务经典乱斗。

它使用单独的原生开关，四种模式默认均关闭；开启后，本局明确标记为“干预局”，不写入常规最高分，避免与自动观战局混在同一成绩口径。它只施加受限物理力，不直接改写据点分数、阵营、黑洞、缩圈、障碍或事件倒计时。

```text
手动干预
上帝之手  推开 / 吸引单位  [关]
```

## 3. 模式兼容策略

首版不要让三个机制在四种模式中任意组合。当前模式已有明确的主目标和节奏，跨模式硬叠加反滚雪球规则会破坏可读性；上帝之手则作为所有模式一致可理解的人工受力能力保留。

| 模式 | 悬赏头名 | 我要打十个 | 上帝之手 | 首版结论 |
| --- | --- | --- | --- | --- |
| 经典乱斗 | 可选 | 可选，和悬赏互斥 | 可选，默认关 | 完整承载反滚雪球与手动干预 |
| 团队占点 | 不开放 | 不开放 | 可选，默认关 | 保留手动站位干预，不叠加额外救场规则 |
| 小心叛徒 | 不开放 | 不开放 | 可选，默认关 | 保留手动站位干预，叛徒仍是唯一翻盘事件 |
| 众生平等 | 不开放 | 不开放 | 可选，默认关 | 保留手动站位干预，响指与障碍仍是模式身份 |

这不是永久删除跨模式可能性，而是先以经典乱斗建立反滚雪球规则的稳定基线；上帝之手从首版起作为跨模式独立能力。后续如确有需求，再为团队占点设计“据点领先悬赏”这一专用变体；不能复用按存活人数判断的旧算法直接开启。

### 3.1 为什么团队占点仅开放上帝之手

团队占点按独立据点分数结算，并且已有弱势援军、道具、黑洞和中心抢点 AI。

- 人数头名不一定是据点分数头名，旧版悬赏目标会误导单位离开中心去追人。
- 我要打十个与绝地求生都会救援弱势方，两个救场机制叠加可能持续拖局。
- 上帝之手允许玩家影响站位，这是“干预局”的明确玩法选择；它不会直接增减据点分数，单位仍必须实际进入据点、按既有压力规则获得分数。
- 力场不能穿透边界、障碍或黑洞核心，也不能取消黑洞吸力、援军、道具或据点结算。玩家能影响路线，但不能绕过模式规则。

### 3.2 为什么小心叛徒和众生平等仅开放上帝之手

- 小心叛徒已有早期标记、救场叛徒、缩圈和黑洞；再加极端翻盘事件会让状态机同时处理多个结算保护条件。
- 众生平等的单次均衡清算已经是主要高光。叠加悬赏或我要打十个会稀释“响指减员 + 障碍”的模式辨识度。
- 上帝之手不会清除叛徒标记、暂停响指清算、改变缩圈边界或移动障碍、黑洞本体；它只在当前规则约束下改变单位的短时速度，因此可与这些模式共存。

## 4. 玩法规则汇总

### 4.1 悬赏头名：持续的反滚雪球

它不是一次性技能，而是当局势明显失衡时出现的“全场围剿领先方”状态。

首版候选规则：

1. 仅经典乱斗可选，默认关闭。
2. 开局前 `5s` 不检查，让玩家先观察基础追捕。
3. 总存活单位不少于 `12`，某阵营人数占比至少 `54%`，且比第二名至少多 `max(4, ceil(总人数 * 0.18))` 人时，成为悬赏头名。
4. 非头名阵营对头名的目标权重提高，但天敌躲避仍高于无脑追击；不能为了悬赏直接送单位。
5. 成功把头名单位转为己方的单位获得：至少一层护盾，以及短时加速。护盾不叠加；加速受既有最高速度限制。
6. 领先优势消失后立即解除悬赏，不残留目标偏置或视觉标记。

视觉与声音：

- 头名阵营单位使用低频金色外圈和小型“悬赏”标记，不覆盖战场。
- HUD 只在触发、换头名、解除时显示一次短消息；不每帧刷新 ArkUI 文本。
- 转化兑现悬赏时走 Canvas 脉冲和已预加载通用事件音。

### 4.2 我要打十个：一次性的极端反杀

它应是明确、少见但可理解的局内高潮，不应由短局随机性决定玩家是否永远看不到。

首版候选规则：

1. 仅经典乱斗可选，默认关闭，且与悬赏头名互斥。
2. 场上仅剩两个阵营；弱势方至少有 `1` 个单位；优势方人数至少是弱势方的 `10` 倍；优势方按基础克制关系本来能克制弱势方。
3. 条件连续成立约 `1s` 后，每局必定触发一次；不继续使用旧版每秒 `10%` 的隐藏随机判定。
4. 若剩余对局时间不足以完整展示事件，则不触发，避免限时结算打断高光。
5. 触发后先冻结模拟约 `1.2s`，显示“背水一战”局部覆盖；随后弱势方获得约 `10s` 暴走。
6. 暴走期间弱势方速度提升，撞到原优势方时执行直接淘汰而非阵营转换；其他阵营关系保持原规则。
7. 每局仅一次。暴走结束后恢复普通克制规则；若弱势方已清场原优势方，则按清场规则结算。

视觉与声音：

- 只给弱势方单位绘制短时强调描边、冲刺尾迹和顶部倒计时条。
- 不使用旧版角色素材；使用新版主题化“背水一战”文案、Canvas 动效和通用事件音。
- 冻结期间不改 ArkUI 页面状态机，暂停和结果判断必须明确区分于玩家主动暂停。

### 4.3 上帝之手：有边界的手动干预

旧版允许持续触摸推开或吸引单位。手机端若无限制保留，会掩盖自动乱斗本身，也会使成绩失真。

首版采用离散脉冲设计：

1. 四种模式均可选，默认关闭；它与当前模式的核心机制同时运行，但不把额外反滚雪球规则带入其他模式。
2. 开局前开启后，本局在 HUD 和结果页标记为“干预局”；任何模式下的干预局均不调用 `recordScore()` 更新常规最高分。
3. 战斗 HUD 显示一个紧凑的原生分段控件：推开 / 吸引，以及剩余干预次数。
4. 每局提供 `3` 次干预脉冲；每次触摸命中战场后在固定半径内施力约 `0.35s`，随后进入约 `2.2s` 冷却。
5. 推开和吸引只改变速度向量与位置趋势，不直接转阵、加分、击杀或触发复活。
6. 单次受力、最大速度和边界约束统一由引擎控制，不能在 `RpsBattlePage.ets` 的触摸回调里直接修改实体数组。

离散脉冲比旧版连续拖拽更适合单手手机操作，也能防止玩家把单位持续推入黑洞、据点或边界。后续若要保留旧版无限制模式，应单独命名为“沙盒观战”，不能混入普通对局。

## 5. 配置页与战斗 HUD

### 5.1 Markdown 线框图

“战局强化”卡位于模式机制之后。经典乱斗同时显示反滚雪球和手动干预；其他模式只显示手动干预：

```text
┌────────────────────────────────────┐
│ 03 战局强化                         │
│ 为本局增加翻盘或手动干预             │
│ ────────────────────────────────── │
│ 反滚雪球                            │
│ [关闭: 已选] [悬赏头名] [我要打十个]│
│ ────────────────────────────────── │
│ 手动干预                            │
│ 上帝之手  推开 / 吸引单位       [关]│
└────────────────────────────────────┘
```

规则：

- 使用一张一级配置卡，内部为扁平行和分段控件，不再嵌套小卡。
- 选择“悬赏头名”后，“我要打十个”自动取消；反向选择同理。
- 关闭反滚雪球规则不影响上帝之手；开启上帝之手不自动启用任何反滚雪球规则。
- 切换模式时，强化选择按目标模式的默认策略重置：反滚雪球规则回到“关闭”，上帝之手回到“关闭”。经典乱斗显示两行；团队占点、小心叛徒、众生平等保留“手动干预”一行。
- 固定底部开始摘要只在选择强化项时追加一项，例如：`经典乱斗 · 悬赏头名 · 标准 · 60 秒`。

### 5.2 战斗态表达

| 机制 | HUD 信息 | Canvas 信息 |
| --- | --- | --- |
| 悬赏头名 | 触发/解除的短消息 | 头名轻标记、兑现奖励脉冲 |
| 我要打十个 | 背水一战倒计时 | 弱势方描边、冲刺尾迹、短时入场强调 |
| 上帝之手 | 推/吸模式、次数、冷却 | 指尖位置短暂力场环 |

任何持续状态都由引擎快照提供。页面层只接收必要的低频 UI 状态，Canvas 继续负责高频战场反馈。

## 6. 类型、规则和模块边界

后续实现遵守 `docs/鸿蒙原生开发规范.md`，只使用 HarmonyOS 原生 ArkTS、ArkUI 与 Canvas。

建议新增或调整的职责：

```text
games/rpsBattle/
  RpsBattleTypes.ets
    - RpsBattleComebackRuleKey: 'none' | 'bounty' | 'tenAgainstOne'
    - RpsBattleEnhancementSelection
    - 悬赏、暴走、手动力场快照类型

  RpsBattleModeConfig.ets
    - 每个模式的强化可用性策略
    - 强化默认值和模式切换时的选择归一化

  RpsBattleBountySystem.ets
    - 头名判定、目标偏置、奖励请求和状态快照

  RpsBattleTenAgainstOneSystem.ets
    - 触发条件、入场冻结、暴走窗口、碰撞改写和状态快照

  RpsBattleGodHandSystem.ets
    - 干预次数、冷却、力场输入快照和单次施力计算

  RpsBattleEnhancementSetupCard.ets
    - “战局强化”配置卡；不把布局继续堆进 SetupPanel

  RpsBattleEngine.ets
    - 持有三个系统，按模式策略重置、更新并提供快照

  RpsBattleRenderer.ets / RpsBattleHud.ets
    - 仅消费快照绘制反馈，不承载规则判断
```

`RpsBattlePage.ets` 只负责把配置选择传给 `RpsBattleOptions`、在任一开启上帝之手的模式中转发触摸坐标、维护暂停/倒计时/结果生命周期；不得把资格判断、人数扫描、碰撞改写或冷却计算放入 ArkUI Builder。

## 7. 冲突规则与执行顺序

### 7.1 选择阶段冲突

| 组合 | 处理方式 | 原因 |
| --- | --- | --- |
| 悬赏头名 + 我要打十个 | 互斥，后选覆盖先选 | 同属反滚雪球规则，叠加不可解释 |
| 我要打十个 + 绝地求生 | 首版不共存 | 都是弱势救场，可能无限续局 |
| 我要打十个 + 叛徒 | 首版不共存 | 叛徒救场会改变两方条件和事件目标 |
| 我要打十个 + 响指减员 | 首版不共存 | 连续两次大幅改变人数，模式身份不清 |
| 上帝之手 + 据点 | 可以共存 | 只施加速度，不能直接加分；据点仍按圈内压力与原有规则结算 |
| 上帝之手 + 黑洞/缩圈/障碍 | 可以共存 | 力场不穿透物理边界，不取消黑洞吸力或缩圈限制，所有碰撞继续由引擎统一处理 |

### 7.2 引擎更新优先级

任一模式启用上帝之手后的建议更新顺序：

```text
读取一次性上帝之手输入
  -> 更新当前模式的时间状态与自动事件
  -> 单位移动、追捕和躲避
  -> 应用上帝之手力场
  -> 应用边界、障碍、黑洞、缩圈等物理约束
  -> 碰撞与当前模式的特殊结算
  -> 胜负判断
```

规则要求：

- 我要打十个的暴走碰撞优先于普通转阵；无暴走时完全回退基础克制。
- 悬赏奖励只在一次普通转阵成功后触发，不因黑洞淘汰、障碍反弹或手动干预凭空发奖。
- 上帝之手输入必须是当帧不可变数据，使用后清空；暂停只取消当前力场，不返还次数或跳过冷却；重开、返回大厅时由引擎完整重置状态。

## 8. 数值与性能边界

| 项目 | 首版边界 |
| --- | --- |
| 悬赏检查 | 至少每 `0.5s` 一次，不在每帧全量排序 |
| 悬赏目标 | 复用阵营缓存和现有目标搜索，不额外扫描全部实体构造对象 |
| 我要打十个 | 每局一次，状态机常数级；暴走只改已有碰撞分支 |
| 上帝之手 | 最多 3 次、固定半径；只遍历可能命中的实体，不在 ArkUI 状态中存实体数组 |
| 总实体数 | 沿用当前 `RPS_BATTLE_MAX_TOTAL_ENTITIES = 60` |
| ArkUI | 不因头名标记、暴走或力场环在每帧刷新页面 `@State` |
| 渲染 | 标记、尾迹、力场全部由既有 Canvas 路径绘制 |

已扩展 `RpsBattlePerf`：

```text
bountyMs
bountyActive/frame
tenAgainstOneMs
tenAgainstOneActive/frame
godHandMs
godHandHits/frame
```

关闭或当前模式不支持某项强化时，对应系统更新、渲染和日志字段应接近 `0.00ms`。

纯规则测试使用 HarmonyOS 官方 Hypium / ArkXTest，放在 `entry/src/ohosTest/ets/test/`；不使用 Node 脚本替代原生测试。

| 测试文件 | 覆盖内容 |
| --- | --- |
| `RpsBattleBountySystem.test.ets` | 开局保护、人数阈值、领先优势解除、悬赏奖励与脉冲清理、关闭状态 |
| `RpsBattleTenAgainstOneSystem.test.ets` | 两方/十倍/克制条件、连续资格、冻结与暴走窗口、碰撞改写、剩余时长保护 |
| `RpsBattleGodHandSystem.test.ets` | 次数、冷却、推/吸方向、作用半径、暂停清理与已消耗次数保留 |
| `RpsBattleEnhancementConfig.test.ets` | 经典乱斗可选反滚雪球、四种模式上帝之手、规则互斥、选项归一化、干预局成绩标记 |

实现阶段至少执行：

```bash
DEVECO_STUDIO_APP=/Volumes/MacSSD/Applications/DevEco-Studio.app ./scripts/build-app.sh --stacktrace
```

设备侧测试包使用 DevEco 模板对应的 `entry/src/ohosTest/module.json5`、`TestAbility` 和
`OpenHarmonyTestRunner`；`@ohos/hypium` 作为项目级 `devDependencies` 管理。这样测试逻辑仍由
HarmonyOS TestKit / Hypium 在设备或模拟器执行，不会引入 Node 或 Web 测试替代方案。

真机验收至少覆盖：

1. 四种模式默认配置与当前版本一致，不因新增卡片发生规则回退。
2. 经典乱斗选择悬赏头名后，领先方被明显标记，优势缩小时奖励和标记正确解除。
3. 经典乱斗选择我要打十个后，满足极端条件时只触发一次，结束后恢复正常克制。
4. 上帝之手在四种模式都可选，次数、冷却、推/吸反馈清晰；据点、黑洞、缩圈、障碍和事件计时仍按原规则工作，且干预局不写入常规最高分。
5. 暂停、重开、返回大厅和模式切换不会遗留强化状态、倒计时、力场或音效。
6. 小屏和常规手机屏中，“战局强化”卡不遮挡固定开始按钮，文字和分段控件不溢出。
7. 观察 `RpsBattlePerf`，默认四模式未开启强化时无持续额外帧耗时。

## 10. 实施结果

1. `RpsBattleEnhancementSetupCard.ets` 已作为独立配置卡接入纵向开局流程；经典乱斗显示反滚雪球单选，四种模式均可开启上帝之手。
2. `RpsBattleBountySystem.ets` 已在经典乱斗中实现人数阈值、目标偏置、转阵奖励和 Canvas 标记。
3. `RpsBattleTenAgainstOneSystem.ets` 已实现连续资格判定、入场冻结、限时暴走和优先淘汰碰撞。
4. `RpsBattleGodHandSystem.ets` 已实现三次离散脉冲、推/吸模式、冷却、边界回收和暂停清理；启用后结果标记为干预局且不写常规最高分。
5. `RpsBattleRenderer.ets`、`RpsBattleHud.ets` 与 `RpsBattlePerformanceLogger.ets` 已消费系统快照，不把规则判断或实体数组写入 ArkUI 高刷状态。

## 11. 实施顺序

1. 先实现强化选择类型、模式可用性和配置卡，但默认全部关闭；完成 UI 与模式切换测试。
2. 实现悬赏头名系统，先只接经典乱斗，观察反滚雪球与帧耗时。
3. 实现我要打十个系统，保持与悬赏互斥，完成冻结、暴走和结算回归。
4. 最后实现上帝之手的跨模式受限脉冲版本，并单独验证四种模式的触摸、成绩隔离和系统返回。
5. 只在真机数据稳定后，评估是否为团队占点设计专用的“据点领先悬赏”；不直接放开旧版人数悬赏。

## 12. 暂不做

- 不改变当前四种模式的默认机制包和胜负规则。
- 不开放所有机制在全部模式中的自由组合。
- 不恢复旧版无限制持续拖拽的上帝之手。
- 不把我要打十个、悬赏或上帝之手做成网络资源、全屏视频或旧版角色素材。
- 不在本轮同时实现多局赛制、下注积分、详细战报或排行榜。

这个设计通过“模式内核心机制 + 经典乱斗可选反滚雪球 + 跨模式独立手动干预”的分层，保留旧版高光内容，同时避免团队占点、叛徒和众生平等因为不适配的反滚雪球规则叠加而失去各自的可读性与平衡边界。
