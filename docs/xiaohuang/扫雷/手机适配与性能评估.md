# 扫雷：手机适配、音量与性能评估

日期：2026-09-18，独立新版首次交付后的体验优化。

## 结论与范围

用户反馈手机高难度棋盘需要横纵拖动、音效偏轻。本轮改为手机随难度缩放，展开的平板／折叠大屏保留原尺寸；提高局内音效数字电平，并评估实际规则开销。仅修改扫雷独立新版及相关文档、测试，不改经典版与水果摊。

扫雷属于低计算量的交互游戏。当前最大棋盘 192 格，没有持续物理模拟、全局求解、每帧布雷或 Canvas 重绘。基准没有发现需要重写算法、增加 Worker 或引入复杂缓存的依据；本轮只减少不必要的计时唤醒、状态刷新与写盘。

## 手机与大屏布局

旧实现统一将格子下限设为 40vp。手机进阶和挑战难度因此超出宽高，即使屏幕本可通过适当缩小显示全部棋盘，也必须拖动。

新规则根据当前窗口短边分流：

- **小于 600vp**：按手机处理。先保证全部列适配宽度，再根据剩余高度缩放；状态卡、难度栏和棋盘标题适当收紧，主操作按钮仍保留 44vp。
- **特别矮的手机窗口**：保留 20vp 格子下限，使用必要的纵向浏览；极窄屏允许按列宽进一步缩小。数字至少 12fp。竖屏把整个棋盘放进页面，避免棋盘内外同时纵向滚动；横屏高度不足时可纵向浏览棋盘，均不需要横向拖动。
- **平板及展开的大折叠屏**：保留 40–58vp 的原有算法和尺寸。半折叠先按完整窗口判定，再选可用区域，避免大屏半折叠时被误认成手机。
- **对局保持**：尺寸改变只重排棋盘，重置滚动偏移，不重新布雷。棋盘已完整容纳时禁用内部滚动，并水平居中。

按用户最后确认，半折叠或其他空间不足的情况允许上下、左右拖动，两个方向按实际溢出分别启用。不会因为窗口尺寸自动遮蔽棋盘、禁止操作或要求先展开／旋转；正常手机、展开大屏和平板的布局可用性优先。

600vp 是布局分界，不依赖具体机型名称。三折叠展开后的大窗口使用原规则，收起为窄窗口后适用手机规则；三折叠实际折痕仍以设备接口返回为准。

## 音效调整

原素材合成振幅系数 0.19，SoundPool 播放音量 0.55，两个环节叠加后，翻格和按钮的播放峰值仅约 0.077 / 0.065。

本轮振幅系数提高到 0.34，左右声道播放增益提高到 0.90：

`20 × log10((0.34 / 0.19) × (0.90 / 0.55)) ≈ +9.33 dB`

8 个 WAV 仍为 24kHz、16bit、单声道，合计 101,392 字节。生成后的素材峰值为 0.210–0.566，单个效果播放后的峰值为 0.189–0.510，没有素材削波，并给混音保留余量。主机测试增加了峰值检查。

这个数字表示数字信号增益，不等同于真实扬声器响度或用户感知的倍数。系统音量、App 声音开关与原有静音／后台停止逻辑保持生效，没有主动调整设备系统音量。真机外放和耳机仍需实际听感验收。

## 规则性能基准

脚本：`scripts/bench-mine-garden-next.mjs`。直接加载真实 `MineModel.ets` 和 `MineEngine.ets`，使用 Node.js 24.14.0、macOS arm64。每种操作预热 200 次后测量 2,000 次；随机种子变化。首次翻格项包含布雷、邻雷计数和空白展开，不包含初始化空棋盘；剩余安全格项完成整局，避免只测无效输入。

本轮主机 P95 结果：

| 操作 | 初探，64 格 | 进阶，130 格 | 挑战，192 格 |
| --- | ---: | ---: | ---: |
| 首次布雷与展开 | 0.0472 ms | 0.0740 ms | 0.1057 ms |
| 打开剩余安全格直到获胜 | 0.0436 ms | 0.1126 ms | 0.2315 ms |
| 复制视图状态、统计并序列化 | 0.0233 ms | 0.0372 ms | 0.0488 ms |
| 校验并恢复存档 | 0.0452 ms | 0.1257 ms | 0.1141 ms |
| 样例存档大小 | 5,180 B | 10,363 B | 15,218 B |

以上是主机 CPU 微基准，排除 ArkUI 布局、GPU、音频播放和 preferences 磁盘刷新，不能换算成真机 FPS、整机功耗或低端设备延迟。当前规则未改动，基准用于判断是否有算法优化必要，没有把测量噪声包装成算法提速。

在 Mate X7 / HarmonyOS 6.1.1 模拟器的挑战对局静置期间，`hidumper --cpuusage` 三次进程采样为 0.26%、0.24%、0.19%；暂停后采样从包含转场的 0.27%、0.24% 降至 0.00%。这只说明该次观测没有持续高 CPU 负载，不是帧率、长时间稳定性或功耗保证。同期整个 App 进程 PSS 为 105,047 kB，其中 ArkTS heap PSS 为 8,979 kB，包含 App 公共层和运行时，不能全算作扫雷的独立占用。

## 已做的性能调整

1. **计时器按状态启停**：仅进行中且没有弹窗时每秒更新一次；开局前、暂停、后台和终局不保留计时器。此前页面存活期间一直每 250ms 唤醒一次。
2. **只刷新可见时间变化**：显示状态按整数秒更新，真实毫秒仍在操作、暂停和退出时按时间差补齐，不改变分数与最佳时间规则。
3. **无效操作不落盘**：旗子已用完、数字周围旗数不匹配时只反馈提示和声音，不再复制整盘状态或立即写存档。
4. **结算只存一次**：去除结算与操作收尾连续保存同一状态的问题。读取终局存档并补报结果时仍会保存上报标记。

有效操作后、定期检查点、暂停、后台与退出的可靠存档保留。没有为节省这点开销扩大断电丢失窗口，也没有改变独立存档格式。

## 验证记录

主机规则测试现为 10 项，增加了手机完整列宽、正常手机高度完整容纳三档、极窄与横屏保留纵向浏览的覆盖。对平板、展开折叠和三折叠尺寸，逐档比较新旧公式得到的格子尺寸一致。

应用构建和测试 HAP 构建通过，成就规则回归通过。原生 Hypium 10 / 10 通过。手机三档分别核对 64／130／192 格可见；长按只插旗，首次翻开正常计时；暂停停在 01:05，继续后为 01:07，后台返回保持暂停。最终挑战档棋盘与底部提示完整可见，展开前后均为 4 / 147，没有重开。

最后一次半折叠原生测试确认横向、纵向拖动都改变了棋盘位置，进度保持 4 / 147，没有误触翻格或要求切换姿态的弹窗。最终原生 10 项回归再次通过。

原生界面与 Hypium 的最终结果同步记录在 [测试报告](../../../测试报告/2026-09-18-扫雷独立新版.md)。基准原始 JSON、音频峰值数据和本轮截图保留于本地忽略目录 `phone-shots/minesweeper-next/`。

## 同日追加：高难度留白、背景与布局过渡

用户随后反馈手机进阶／挑战卡片边缘空隙，并授权调整代码后直接提交推送，页面由用户自行检查。此次追加不启动模拟器或查看页面，下面尺寸为布局函数结果，不是截图测量。

- 手机顶部标题从 56vp 收至 52vp，状态卡从 68vp 收至 60vp，难度栏从 52vp 收至 48vp；模式栏减少外边距，按键本体仍为 44vp。控件、间距与布局预算共用尺寸常量，减少两处数值不同步。
- 手机卡片按实际棋盘宽高收紧，不再用固定空白撑满；左右各保留约 12vp，标题、提示和内边距继续保留。高度适配采用 0.25vp 步长，减少 16 行棋盘整数取整带来的空隙。
- 在宽度受限的初探棋盘下方仍可有自然余白，不把正方形格子拉成长方形或无上限放大。正常手机三档完整容纳，极矮手机竖屏仍通过页面纵向浏览；横屏及半折叠继续按溢出方向滚动。

使用顶部 28vp、底部 20vp 安全区，布局计算结果如下：

| 窗口（vp） | 初探格子 | 进阶格子 | 挑战格子 |
| --- | ---: | ---: | ---: |
| 345 × 782 | 37vp | 29vp | 24vp |
| 390 × 844 | 42vp | 34vp | 28vp |
| 430 × 932 | 47vp | 38vp | 31vp |
| 768 × 1024 | 52vp | 42vp | 40vp |
| 1280 × 800 | 58vp | 40vp | 40vp |
| 1600 × 1000 | 58vp | 54vp | 44vp |

390 × 844 的进阶／挑战此前为 32／26vp，现在为 34／28vp。大屏仍使用此前的 40–58vp 计算规则，测试逐档比较公式保持一致；不会随屏幕无限放大。

背景从整张 Cover 图片改成四层定位 SVG：底部柔和渐变地面、右上等高线、左右带叶脉的植物与少量暖金细节。浅深色共 8 张背景 SVG，合计 5,298 字节；全套 SVG 从 121 增至 127 个。背景不参与命中或无障碍焦点，无粒子循环、常驻动画或新增计时器。

展开／收起、旋转和难度导致的有效布局变化使用 200ms EaseOut 原生过渡，棋盘和控制区设置对应的几何过渡标识，支持上下排布与侧栏排布之间切换。重复的安全区／窗口通知不重启动画，首次载入直接定位。对局引擎、格子数据和存档格式不因布局变化重置。按压的 90ms 缩放与棋盘尺寸动画分开。

主机规则／布局检查扩展为 11 项并通过，覆盖收紧后的手机三档、短窗口滚动、重复通知过滤、大屏原尺寸以及半折叠两轴滚动；127 个 SVG 通过 XML 解析。应用构建通过。共享工作区的测试包构建遇到水果摊未提交测试的类型错误，因此在基于 `15c8264`、仅叠加本轮扫雷源码／资源／测试的临时副本中完成测试 HAP 构建，结果通过，没有改动另一位 Agent 的文件。此次没有运行原生 Hypium、进行画面验收或重新测量 GPU 动画性能，前述原生记录属于追加调整之前；实际视觉与过渡效果待用户查看。
