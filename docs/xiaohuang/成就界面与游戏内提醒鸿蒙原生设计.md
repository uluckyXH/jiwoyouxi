# 成就界面与游戏内提醒鸿蒙原生设计

日期：2026-08-27
状态：成就判定、队列和扫雷事实上报已实现；首版顶部大卡片已替换为轻量“成就落款”，勋章图片槽位与成就页 DEV 清除入口也已落地。

关联文档：

- [成就系统统一设计方案](成就系统统一设计方案.md)：定义成就数据、判定、存档和游戏接入契约。
- [成就墙与解锁反馈体验设计](成就墙与解锁反馈体验设计.md)：定义首期六款游戏的成就内容、触发事实与产品范围。

本文只回答两个体验问题：大厅里的成就界面具体长什么样，以及玩家在游戏中达成成就时，如何以 HarmonyOS 原生方式得到清晰但不打断操作的提醒。

实现状态（2026-08-27）：成就墙已读取独立真实状态；扫雷已接入结算事实上报，顶部提醒的判定、去重、FIFO 队列、计时器清理和不抢触摸均已落地。首版 `276vp × 70vp` 的“Logo + 占位徽章 + 三行文字”大卡片已被替换为 `236vp × 46vp` 的单行胶囊；本轮没有改动任何 `games/**` 游戏代码。

## 0. 实测复盘：为什么首版看起来不对

首版的技术路线没有问题，视觉却有三个根本问题：

- 同时放了游戏 Logo、占位徽章、标题和说明，信息密度像一张缩小的结果卡，而不是一次轻反馈；
- `70vp` 高、实体奶油底、明显阴影和高光星点都在争夺注意力，恰好又与扫雷的结果层同屏；
- 目前没有正式勋章图时，两个身份图形并排会更像临时占位，而不是有意设计的视觉语言。

因此，“等勋章 PNG 做好”并不能解决问题；图片只会替换左侧内容，无法修复大卡片的层级、体积和动效节奏。

### 0.1 已触发过还会不会再次弹出

不会。成就引擎只把首次达到条件的条目放进 `newlyUnlocked`：首次解锁会保存 `unlockedAt`，之后再次完成同一条件只更新或保持进度，不再次进入通知队列。应用重启后也不会补播历史提示。

这是正式体验应有的行为，避免玩家每局都被同一成就打断。为便于反复验证真实链路，成就页当前常驻 **DEV · 清除本机成就** 入口：它把独立成就状态恢复为空，再通过新开一局的真实上报重新触发提示。该入口会一直保留到项目负责人明确要求隐藏或移除，具体边界见 [5.3 DEV 成就重置入口（当前常驻）](#53-dev-成就重置入口当前常驻)。

如果后续需要只看视觉、不想重新游玩，再另做独立的“通知预览”；预览只向组件注入固定展示样例，绝不写入成就状态、清空存档或伪造游戏事件。

## 1. 新方案结论：轻量“成就落款”

保留“游戏不显示通知、应用壳统一队列”的架构，但废弃首版顶部大卡片。新的游戏内反馈改为一条轻、短、像落款而非弹窗的 `AchievementRibbon`：

```text
                        ╭────────────────────────╮
                        │  ✦  新成就 · 平安出窝   │
                        ╰────────────────────────╯
                         轻入场，短暂停留，淡出
```

它只回答一件事：“你刚获得了哪一项成就？”详细条件、来源游戏、日期和多项回顾留给结算页 / 成就墙，不在游玩瞬间重复塞进一张大卡。

| 项目 | 新规范 |
| --- | --- |
| 命名 | 对外文案统一为“新成就”；实现文件保持 `AchievementUnlockNotice`，不为这次视觉改造重命名或拆分。 |
| 尺寸 | 当前固定为 `236vp × 46vp`，圆角为高度的一半；不再使用 `276vp × 70vp`。 |
| 内容 | 一个小印记 + `新成就 · 成就名称` 单行；只在名称过长时省略，**不显示游戏 Logo、第二枚徽章、第三行说明**。 |
| 无勋章图片时 | 使用稳定的小型占位符号 / 圆形印记。对应 PNG 落盘后，同一位置自动改为图片，不需改游戏逻辑。 |
| 材质 | 低对比半透明暖灰或深暖灰、细边线、极弱阴影；当前不启用 `backdropBlur`，避免为玻璃感牺牲稳定可读性。 |
| 高光成就 | 只提升左侧印记边线为暖金；取消漂浮星点、粒子和缩放脉冲。 |
| 输入 | 继续 `HitTestMode.None`，完全不抢棋盘、按键或结果页按钮。 |

新方案的关键是**删减**：游戏本身已经告诉玩家正在玩什么，成就页会保存完整信息，短提示无需再放 Logo、假徽章和说明三套身份。

### 1.1 弹窗实际效果：温暖的轻磨砂，不是厚卡片

它会被叫作“弹窗”，但实际视觉更像短暂浮在游戏上方的一枚磨砂落款：**半透明，但不是能清楚看到背后内容的透明玻璃。**

以扫雷结算为例，结果层稳定约 `350ms` 后，顶部先出现一条 `236vp × 46vp` 的小胶囊：

```text
背后的棋盘 / 结果层只透出模糊色块

                 ╭────────────────────────╮
                 │  ✦  新成就 · 平安出窝   │
                 ╰────────────────────────╯
                    约 1.5 秒后安静淡出
```

动效不是“砰”地弹出来：它从上方约 `8vp` 处以低透明度轻落到位，`180ms` 内稳定；正常成就停留约 `1.5s`，再在 `180ms` 内略向上淡出。高光成就只让左侧印记细描边变为暖金，不播放星星、粒子、扫光、缩放或大幅弹跳。

| 层 | 浅色模式 | 深色模式 | 感受 |
| --- | --- | --- | --- |
| 主材质 | 暖白半透明面 `rgba(255,250,240,0.92)` | 深咖半透明面 `rgba(36,32,28,0.92)` | 类似温润的磨砂亚克力 / 牛奶玻璃，不是纸片、也不是镜面玻璃。 |
| 背景内容 | 只允许透出约一成左右的颜色与明暗 | 同左 | 能感到它浮在游戏上，但不会让棋盘纹理干扰文字。 |
| 边缘 | `1vp` 柔和暖棕描边 | `1vp` 微暖白描边 | 让胶囊从复杂游戏背景中分离，不做强高光。 |
| 阴影 | 极弱、短距离的暖灰阴影 | 极弱、短距离的黑色阴影 | 只提供层级，不制造厚重悬浮卡效果。 |
| 文字 | 深棕单行文字 | 米白单行文字 | 始终高对比、最多一行，不依赖背景模糊才可读。 |

当前实现不使用 `backdropBlur`，基础设计在不启用模糊时也成立。若之后真机确认复杂棋盘上文字仍清晰、没有可感知性能成本，再单独评估是否增加这一增强项；不能为了“玻璃感”让提示变得飘、亮或糊。[ArkUI 背景模糊参考](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-arkui-145)

### 1.2 两类界面的分工

成就体验仍分为两个互相配合的界面：

1. 大厅“成就墙”：像一本轻量的勋章收集册，用于浏览、筛选、查看进度与回顾历史。
2. 游戏内“成就落款”：顶部居中的非阻断单行提示，只告诉玩家“刚刚完成了什么”；不会暂停、不会要求点击确认，也不会吞掉触摸输入。

```text
大厅：看收藏和进度                    游戏中：只给短暂、明确的一行反馈
┌──────────────────────┐             ┌──────────────────────────┐
│ 成就墙          8 / 22│             │     ✦ 新成就 · 西瓜到手 │
│ ━━━━━━━━━━━░░░░       │             └──────────────────────────┘
│ [全部][已解锁][进行中] │                   自动淡出，不拦截操作
│ 合集里程碑             │
│ 游戏分组与勋章条目     │
└──────────────────────┘
```

成就详情 Sheet 只在玩家主动点击成就条目时使用；它承载条件、进度、解锁日期和后续完整勋章图。游戏内提示不再承担这些信息。

## 2. 成就墙：页面视觉设计

### 2.1 页面气质

成就页延续鸡窝游戏现有的奶油、纸张、轻玻璃质感，但视觉主题从普通“设置列表”切到“收集到的小勋章”。重点是温暖、清楚、可扫读，而不是堆叠大量金色卡片或做一张新的营销横幅。

- 合集成就使用鸡蛋黄、羽毛绿、木板棕作为共同身份。
- 每款游戏使用其 `GameRegistry` 中已有的 Logo 与主题色，只在局部点缀，不给整页铺满高饱和颜色。
- 已解锁像“收进册子的勋章”：暖金高光、清晰勾选和日期。
- 未解锁不是灰掉的问号：保留名称和条件，让玩家知道下一步可以追求什么。
- 有进度时优先显示细进度条和 `当前 / 目标`，不使用大号百分比抢走游戏内容。

### 2.2 手机主界面线框

以下是以项目默认 `390vp` 手机画布为基准的视觉层级；宽屏仍沿用 `CoopViewport` 的手机画布策略，不把成就条目无限拉宽。

### 2.3 尺寸、层级与交互

| 区域 | 设计规格 | 交互 |
| --- | --- | --- |
| 页边距 | 与大厅一致，左右 `20vp`；组间距 `18–20vp` | 页面在现有 `Scroll` 内滚动，底部留出 Tab 安全空间。 |
| 标题区 | 标题 `22vp`，副标题 `12–13vp`，右侧只显示 `已解锁 X / Y` | 不做跳转，不增加 Banner。 |
| 总进度 | `4–6vp` 高的细条，已完成部分用暖金色 | 只表达总体收集感，不显示夸张百分比。 |
| 筛选器 | 高 `34–38vp` 的三段胶囊，默认“全部” | 点击切换“全部 / 已解锁 / 进行中”，列表以轻微淡入、上移切换。 |
| 分组标题 | Logo `28vp` + 游戏名 + 右侧 `X / Y` | 仅作分组身份；首版不需要折叠，减少额外状态。 |
| 成就条目 | 高约 `72–84vp`，圆角 `16–18vp`，一行一张轻卡片 | 点击打开详情 Sheet，不在条目上放多个小按钮。 |
| 徽章格 | `48vp × 48vp`，圆角 `14–16vp` | 勋章图或占位符表达成就语义；游戏来源由分组 Logo 与名称表达，不能只依赖颜色。 |

每条成就严格保持三栏：左侧徽章、中间标题与条件 / 进度、右侧状态。这样在文字变长、深色模式、系统字体稍放大时，信息仍能稳定排布。

```text
┌─────────────────────────────────────────┐
│ [48 徽章]  成就标题                  已解锁 │
│             条件或简短事实说明    2026-08-24│
│             6 / 10  ━━━━━━━━━░░░         │
└─────────────────────────────────────────┘
```

规则：

- 已解锁的右侧优先显示“已解锁”，日期放在次级文字；没有日期的成就不能伪造日期。
- 未解锁但可量化的条目显示 `6 / 10` 和细进度；一次性条件显示“未达成”。
- 条件文字最多两行，超出时省略，不允许把徽章或右侧状态挤出屏幕。
- “进行中”筛选包含未解锁条目；即使当前没有数值进度，也展示可读条件。
- “已解锁”筛选为空时显示一个轻量空态：“再玩一局，把第一枚勋章带回鸡窝。”不显示空白大插画。

### 2.4 徽章图标语言

首版不需要为 22 条成就各画一张位图插画。建议实现一个可复用的 `AchievementBadge`：游戏 Logo 表示“来自哪里”，语义符号表示“为什么解锁”。

| 语义 | 图标方向 | 适用示例 |
| --- | --- | --- |
| 开始 / 首次 | 星星、鸡蛋、小屋 | 鸡窝开张、初入战场、首次排雷成功 |
| 胜利 / 完成 | 勾选、皇冠、奖章 | 四花归位、平安出窝 |
| 技巧 | 闪电、四格、连线 | 第一记四消、转化风暴 |
| 时间 / 效率 | 时钟、羽毛 | 疾速清台、迅捷排雷 |
| 收集 / 里程碑 | 爱心、收藏夹、六角星 | 常玩收藏、六边形鸡仔 |
| 关键高光 | 金色西瓜、冠星 | 2048 达成、最终合成 |

- 正式素材优先使用 ArkUI `SymbolGlyph` 或项目统一的矢量 / 位图资源；当前没有勋章图片时，成就墙使用注册表的 `placeholderSymbol` 作为过渡。游戏内成就落款始终只保留一个小印记，不让游戏页持有图片或图标逻辑。
- 游戏主题色从 `GameRegistry` 的 `accent` 取得，使用低透明度底色；重要状态才用暖金色加强，不让所有徽章都像稀有奖励。
- 候选 token 集中到 `design/AchievementTheme.ets`，例如 `gold`、`goldSoft`、`lockedSurface`、`lockedInk`、`progressTrack`，不能继续在 `HubPage.ets` 散落色值。
- 深色模式降低背景亮度、保留金色和文字对比；不能仅通过降低整体透明度让锁定文字失读。

### 2.5 成就详情 Sheet

点击单条成就后，使用底部半模态详情，而不是跳转新页。它是玩家主动发起的浏览动作，因此可以使用 `bindSheet` 或自定义详情弹窗。

```text
┌──────────────────────────────────────┐
│                ━━━━━                  │
│             [大号成就徽章]             │
│              西瓜到手                  │
│       在鸡窝水果摊首次合成西瓜           │
│                                      │
│  当前状态   已解锁                      │
│  解锁时间   2026-08-24 14:30            │
│  来源游戏   鸡窝水果摊                  │
│                                      │
│              [ 知道了 ]                │
└──────────────────────────────────────┘
```

未解锁时把“解锁时间”替换为“达成条件”或“当前进度”。详情中不加入分享、领奖、货币、广告或任务跳转；首期的成就是纯收集与回顾。

## 3. 游戏内提醒：轻量成就落款

### 3.1 位置与视觉规格

成就落款固定在顶部安全视觉区，水平居中。它是短暂的悬浮信息，不是游戏的新 HUD，也不是一张缩小的结果卡。

```text
┌──────────────────── 手机屏幕 ────────────────────┐
│ 系统安全区                                         │
│                                                    │
│              ╭──────────────────────╮              │
│              │ ✦ 新成就 · 平安出窝  │              │
│              ╰──────────────────────╯              │
│                 游戏顶部栏 / HUD                    │
│                                                    │
│                 棋盘 / Canvas / 操作区             │
│                                                    │
│                 底部按键或系统手势区               │
└────────────────────────────────────────────────────┘
```

| 项目 | 新视觉规格 |
| --- | --- |
| 位置 | 顶部居中，以 `CoopViewport` 的手机画布为参照；目标为安全区下 `20–24vp`。若某款游戏真实 HUD 冲突，由应用壳提供展示 inset，游戏页不自行写浮层。 |
| 尺寸 | 当前宽 `236vp`、高 `46vp`；标题过长时单行省略。 |
| 内容 | 左侧 `34vp` 圆形印记格，内含 `28vp` PNG 或占位符；右侧只有 `新成就 · 成就名称`，汇总时为 `本局新解锁 X 项成就`。不显示 Logo、第二枚徽章、说明或日期。 |
| 背景 | 半透明暖灰 / 深暖灰、`1vp` 低对比边线、极弱阴影；真机对比度足够时才考虑极轻 `backdropBlur`。 |
| 色彩 | 普通解锁使用低饱和印记；高光成就只提升印记与描边为暖金，背景不换成大面积金色。 |
| 输入 | 完全不响应点击和手势，继续使用 `HitTestMode.None`。 |
| 层级 | 只在对应游戏仍可见时显示；继续避让进入身份胶囊、场景转场、离开确认与页面销毁。 |

正式勋章素材完成后，只需在对应 `AchievementRegistry` 条目填写 `badgeAssetPath`。成就墙列表、详情 Sheet 和游戏内落款会复用同一张图片：落款仍只占一个 `28vp` 小印记位，因此不会回到“两个图标并排、再加三行文字”的问题。

### 3.2 动效：像一次确认，不像庆典弹窗

| 类型 | 适用场景 | 目标时长与效果 |
| --- | --- | --- |
| 普通落款 | 首局、普通胜利、累计局数 | `180ms` 淡入下落、约 `1.5s` 停留、`180ms` 淡出。 |
| 高光落款 | 2048、第一记四消、合成西瓜、最终合成 | 停留约 `1.8s`，只提升印记描边色；不添加星点、羽毛、粒子或缩放脉冲。 |
| 汇总落款 | 同一批次超过当前单项上限 | 只显示数量；完整名称由成就墙承担。 |

当前只动画 `opacity`、`translate`，不动画胶囊宽高或缩放，也不触碰棋盘、Canvas 或结果层的布局状态。内部状态变化沿用 ArkUI 的 `animateTo` / `.animation()`；这一用法也符合华为对属性动画的性能建议。[ArkUI 动画使用指南](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-animation-usage-guide)

上述 `180ms + 1.5s / 1.8s + 180ms` 已写入 `CoopMotion` 并由当前胶囊组件使用。

### 3.3 何时出现：先让游戏完成自己的反馈

原则是：**成就可以立即判定和保存，视觉落款一定排在游戏自身高光之后。**

| 游戏 | 成就 | 安全展示时机 |
| --- | --- | --- |
| `rpsBattle` | 首局、支持阵营获胜、转化风暴 | 结果层稳定后。 |
| `freecell` | 通关、少步、限时 | 胜利结果层出现后。 |
| `minesweeper` | 胜利、快速、插旗 | 结果层稳定后；当前扫雷已采用约 `350ms` 后上报。 |
| `chicken2048` | 256、1024、2048 | 合成动画、分数变化和棋盘状态稳定后；不能在手势滑动中插入。 |
| `tetris` | 第一记四消 | 消行动画完成、落块稳定后；其他结算型成就在结算层后。 |
| `suika` | 西瓜、最终合成 | 合成和物理反馈结束后；普通分数类在结算后。 |

以下时机一律延后：

- 游戏刚进入时的 `GameEntryBadge` 仍在显示；
- 暂停、玩法说明、离开确认、失败确认等阻断型覆盖层正在显示；
- 页面正在切入 / 切出，或当前游戏已经离开；
- 同一局的前一条成就落款尚未结束。

未来每个游戏的结果层可增加一行只读的“本局新成就”回看区，让顶部提示消失后仍可查看结果；这属于各游戏接入时的独立 UI 工作，**不在本次提醒组件改造中触碰游戏页面**。

### 3.4 多项成就与重复触发

```text
游戏事实上报
  -> 成就引擎返回 newlyUnlocked（仅首次解锁）
  -> 先持久化解锁状态
  -> 应用壳转换为展示项并进入内存队列
  -> 等待安全展示时机
  -> 显示一条成就落款
  -> 淡出后再显示下一条 / 汇总条
```

已确认并继续保留的规则：

- **同一次满足两项或三项新成就：依次展示。** `Index.ets` 以 FIFO 入队，前一条卸载后才挂载下一条；不会叠放、并排或同时播放。
- 当前单次 `newlyUnlocked` 最多逐条展示 3 项；第 4 项及之后生成 1 条汇总落款，排在前三项之后。
- 已解锁成就不再进入 `newlyUnlocked`，所以无论再次通关、重复完成条件、应用重启，都不会再触发该成就的提示。
- 重复 `eventId` 和非正式事件会被引擎忽略；队列只存在内存中，退出应用不补播旧提醒。
- 通知不做点击跳转，保持 `HitTestMode.None`，不与拖拽、滑动、按键竞争输入。

首局扫雷可能一次得到“鸡窝开张”“平安出窝”“迅捷排雷”“旗开得胜”四项：前三项依次显示，第四项以汇总落款出现。这是**当前已实现、且此前确认过的队列行为**。如果后续认为首次 4 项仍过于密集，可另行确认“同一结算 2 项以上直接汇总”的产品规则；该变更会改变已确认的逐条提醒体验，不能在只改视觉时擅自切换。

队列顺序的纯逻辑由 `AchievementNotice.test.ets` 覆盖；真机接入时还必须观察连续落款无重叠、无输入拦截。

## 4. HarmonyOS 原生实现选型

### 4.1 推荐方案：继续使用 `Index.ets` 根 `Stack` 的声明式浮层

鸿蒙确实有更强的 `OverlayManager`，但**更换弹窗 API 不会自动让视觉变好**。当前项目最合适的方案仍是把 `AchievementUnlockNotice` 挂在 [Index.ets](../../entry/src/main/ets/pages/Index.ets) 的根 `Stack`，它已经按“轻量成就落款”的视觉落地，由 `Index.ets` 统一维护通知队列和显示状态。

理由：

- `Index.ets` 已经是所有游戏的共同路由、存档入口，并且已有根级 [GameEntryBadge.ets](../../entry/src/main/ets/shell/GameEntryBadge.ets)。
- `GameEntryBadge` 已经验证了顶部居中、`opacity + translate`、计时器清理和 `HitTestMode.None` 这条实现路径；成就落款可以复用同样的可靠边界。
- 成就判定、存档、队列和 UI 只需要一个所有权，不会让六个游戏各自维护 Toast、计时器和重复逻辑。
- 当前是单 `Index` 编排的应用，不需要为了一个小胶囊过早引入更复杂的全局 Overlay 生命周期。

建议的根层级：

```text
Index 根 Stack
  ├─ GameSceneTransition（大厅或当前游戏）
  ├─ GameEntryBadge（短暂的进入身份胶囊）
  └─ AchievementUnlockNotice（轻量成就落款）
```

`GameEntryBadge` 与成就落款不同时展示。通知队列在前者卸载后才开始播放。阻断型覆盖层的等待由每款游戏在自身反馈稳定后再上报事实来保证；扫雷已按这一边界接入。

### 4.2 鸿蒙原生能力的取舍

HarmonyOS 官方的弹窗选型中，Toast 面向简单即时反馈，`OverlayManager` 面向完全自定义的浮层 / 胶囊，而 `bindSheet` 与 Dialog 适合覆盖旧界面的交互内容。[ArkUI 弹窗概述](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/arkts-dialog-overview)

| 方案 | 是否用于游戏内解锁 | 原因 |
| --- | --- | --- |
| 根 `Stack` 声明式浮层 | **现在继续采用** | 与现有 `Index.ets` 状态流、`GameEntryBadge`、队列和计时器完全一致；能精确控制单行胶囊的层级、深浅色与不抢触摸。 |
| `OverlayManager` | 有明确需要时再迁移 | 官方特别适合完全自定义的悬浮球 / 胶囊。若以后有多 `Navigation` 页面、通知必须跨页面独立存活，或根层不再是唯一壳，再将同一队列协调器迁移过去。 |
| `promptAction.showToast` | 不采用 | Toast 适合简单的即时文字反馈；成就需要受控队列、与进入胶囊避让和统一视觉，系统 Toast 不合适。 |
| `bindPopup` | 不采用 | Popup 的语义是依附某个锚点的说明气泡；成就不是某颗按钮的说明，也不应因锚点、自动关闭或遮罩配置与游戏交互耦合。 |
| `CustomDialog` | 不采用 | 是面向确认 / 操作的模态内容，可能拦截系统返回和游戏触摸，不适合“玩着玩着”的短提示。 |
| `bindSheet` | 只用于详情 | 玩家主动点击成就时查看完整条件、进度与解锁时间。 |

结论：**用根 `Stack` 做轻量落款，是当前工程中最简洁也最符合鸿蒙能力边界的做法；`OverlayManager` 是未来架构变化时的升级路径，不是为修复“丑”而必须引入的依赖。**

### 4.3 动画和触摸的原生做法

- 成就落款内部的透明度和位移使用 `UIContext.animateTo` 与组件 `.animation()`；当前不使用缩放，避免它显得像一个大弹窗。
- 华为的 ArkUI 动画指南建议使用系统动画能力，并尽量用 `opacity`、`translate`、`scale` 等图形变换，而不是频繁修改布局属性；当前选择前两者，适合短暂提示。[ArkUI 动画使用指南](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-animation-usage-guide)
- 通知外层设置 `.hitTestBehavior(HitTestMode.None)`。官方的触摸测试控制支持通过该模式使浮层不参与自身触摸响应，从而不抢走棋盘点击、拖拽和底部按键。[触摸测试控制参考](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/ts-universal-attributes-hit-test-behavior)
- 无勋章图片时，当前使用注册表内稳定的单字符占位符；等 PNG 资源落盘后由 `badgeAssetPath` 自动替换。若后续统一切换到 `SymbolGlyph`，必须先确认系统资源存在，不能猜测资源名称。[SymbolGlyph 组件参考](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/arkts-common-components-symbol)
- 仅在入场 / 出场更新小而稳定的状态字段，Canvas 游戏的实体数组、物理状态和 ArkUI 页面状态不要因通知而每帧刷新。

### 4.4 建议文件边界

| 文件 | 职责 |
| --- | --- |
| `shell/AchievementModule.ets` | 成就、进度、结算结果、即时事件和通知数据类型。 |
| `shell/AchievementRegistry.ets` | 静态成就目录、标题、图标语义、`badgeAssetPath`、游戏归属、展示等级。 |
| `shell/AchievementEngine.ets` | 纯判定：输入独立成就状态与玩法事实，输出新进度和 `newlyUnlocked`。 |
| `shell/AchievementNotice.ets` | 纯展示数据转换：过滤无效项、生成单条落款，并在一批解锁超过 3 条时生成汇总项。 |
| `design/AchievementTheme.ets` / `design/CoopMotion.ets` | 通知的尺寸、颜色与动画时长 token，避免在组件或游戏页散落常量。 |
| `components/AchievementUnlockNotice.ets` | 顶部非阻断的成就落款；保持现有文件名，不为视觉调整额外重构。 |
| `pages/AchievementWall.ets` | 成就墙、筛选和分组列表；不写玩法阈值。 |
| `pages/Index.ets` | 唯一的队列所有者：接收事件结果、协调通知与进入胶囊，并在离开时清理计时器。 |

## 5. 状态流和接口约束

### 5.1 游戏页只报告事实

原有 `recordScore(score)`、结果页和游戏玩法保持原样。成就接入只在已有稳定出口旁追加一个 `AchievementGateway.reportAchievementEvent` 回调，分为结算事实与可选即时里程碑：

```text
正常结算：reportAchievementEvent({ type: 'sessionEnd', facts: ... })
高光瞬间：reportAchievementEvent({ type: 'milestone', facts: ... })
```

例如：

- 2048 在合成时报告 `maxTile`，引擎决定是否首次达到 256 / 1024 / 2048。
- 俄罗斯方块在结算时报告 `lines`、`level`，在四消完成后可报告一次高光事实。
- 水果摊在合成反馈完成后报告 `mergeLevel` 或 `isFinalMerge`。
- 扫雷目前已按此约束上报结算事实；它没有导入或渲染通知组件。
- 游戏不得直接写某个成就 ID、直接显示落款、直接访问 `preferences`，更不得为视觉改造拆分、重排或修改既有玩法代码。

### 5.2 `Index.ets` 的通知协调职责

`Index.ets` 新增的状态应保持小且稳定：当前通知、是否已挂载 / 可见、内存队列和少量计时器。做法应参考现有 `showEntryBadge()`、`hideEntryBadge()` 与 `clearEntryBadgeTimers()`，并在 `aboutToDisappear()` 中清理所有成就通知计时器。

建议的执行顺序：

1. 收到结算或即时事件，先让 `AchievementEngine` 判定。
2. `AchievementService` 先保存独立的成就状态与已解锁时间；游戏记录仍沿用原有路径，两者不互相推导。
3. 仅把本次真正新解锁且可提示的条目加入内存队列。
4. 若进入胶囊、场景转场、返回大厅或已有通知正在显示，则等待；游戏自己的阻断覆盖层应在稳定后才上报事实。
5. 展示结束后清理当前通知，再处理下一条或汇总条。

通知组件只读取 `AchievementNoticeItem`，其中有 `achievementIds`、`gameId`、标题、短说明、占位符号、`badgeAssetPath` 和展示等级。新视觉只读取标题、勋章图路径、占位符和展示等级；`summary` 仍可保留在展示数据内供成就墙或未来结果回看使用，不能由组件二次判定或读写存档。

### 5.3 DEV 成就重置入口（当前常驻）

为了让你能在不卸载 App、不清除全部本机数据的情况下反复测试“首次解锁 → 顶部落款 → 成就墙更新”这条真实链路，成就页当前常驻提供一个 **DEV · 清除本机成就** 工具。按当前约定，它不会随构建模式自动隐藏；只有项目负责人明确提出时才隐藏或移除。

它不是通知预览，也不是游戏作弊器；它只把独立成就状态恢复到全新的空状态。下一次通过真实游戏事件达成条件时，引擎会再次把该成就视为首次解锁，并正常播放落款。

#### 5.3.1 成就页中的位置与交互

入口放在“成就墙”总进度条与筛选栏之间，避免每次测试都要滚到页面底部；它必须明显标记为开发工具，且不能伪装成普通玩家功能。

```text
┌──────────────────────────────────────┐
│  ♕ 成就墙                       4 / 22 │
│  ━━━━━━━━━━━━━━━░░░░░              │
│                                      │
│  DEV 工具                            │
│  [ DEV · 清除本机成就 ]              │
│  仅清除成就进度，不影响游戏数据       │
│                                      │
│  [ 全部 ] [ 已解锁 ] [ 进行中 ]       │
└──────────────────────────────────────┘
```

按钮采用低饱和暖红描边、透明底、`40vp` 以上点击热区，不使用醒目的实心危险色。点击后打开一个小型确认 Sheet，而不是立即清除：

```text
清除本机成就？

会清除本机独立成就进度、首次解锁时间和事件去重记录。
不会影响：最高分、游玩记录、收藏、设置、各游戏存档。

[取消]                         [清除成就]
```

- 点击“取消”、关闭 Sheet 或返回：不写入任何数据。
- 点击“清除成就”：按钮进入短暂 loading 状态，阻止重复点击；成功后关闭 Sheet、将筛选切回“全部”，页面立即显示 `0 / 总数`。
- 成功提示只在成就页内显示一条小字“已清除本机成就；完成新一局可再次触发提示”，**不**调用游戏内成就落款，以免把“清除操作”伪造成解锁。
- 保存失败时保持原页面状态并显示“清除失败，请重试”；不能先把 UI 归零再假装成功。

#### 5.3.2 数据边界：只重置 `achievement_state`

| 数据 | DEV 清除后的结果 |
| --- | --- |
| `achievement_state.progresses` | 清空；全部成就恢复未解锁。 |
| `achievement_state.processedEventIds` | 清空；新开局产生的新 `eventId` 可以正常参与判定。 |
| `achievement_state.completedSessionCount` / `playedGameIds` | 恢复为空；合集成就也从零开始。 |
| 顶部成就通知内存队列 | 清空；不得在回到游戏后播放重置前遗留的提示。 |
| `snapshot.records`、最高分、游玩次数、最近游玩 | **保持不变。** |
| 收藏、声音、触感、外观模式 | **保持不变。** |
| 各游戏自己的局内 / 本地存档 | **保持不变。** |

实现时必须调用 `emptyAchievementState()` 生成规范空状态，并经 `AchievementService` / `CoopStorage.saveAchievementState()` 持久化；禁止调用 Preferences 的 `clear()`、删除整个存储文件，或重置 `snapshot`。这样即使 DEV 工具被误点，也只影响成就这一块可再获得的数据。

`AchievementWall` 只能请求重置，不能自行读写存储；回调链保持为：

```text
AchievementWall（DEV 按钮 / 确认 Sheet）
  -> HubPage（透传回调）
  -> Index.ets（清除通知队列、更新 @State）
  -> AchievementService.reset(context)
  -> CoopStorage.saveAchievementState(emptyAchievementState())
```

`CoopStorage.saveAchievementState()` 现在会返回明确的 `boolean`。只有持久化成功后，`AchievementService` 才更新内存状态，`Index.ets` 才更新 `achievementState` 并清空通知队列；失败时页面保留原状态并显示重试提示。

#### 5.3.3 当前可见性与隐藏条件

- 当前按钮在成就页常驻可见，且 `AchievementWall` 始终接收重置回调；这是为了反复测试真实上报链路的明确产品决定，不依赖 Preferences、手势彩蛋或设备环境。
- 入口仍只标为 DEV 工具，采用确认 Sheet；它不属于游戏玩法，也不能从任何 `games/**` 页面调用。
- 当项目负责人要求隐藏时，优先在 `AchievementWall` 停止渲染 DEV 工具并停止从 `HubPage` 透传回调；保留 `AchievementService.reset()` 仅作为应用壳的受控测试能力，除非明确要求一并删除。

#### 5.3.4 DEV 重置验收

1. 成就页始终能看到“DEV”“清除本机成就”文字和按钮，且入口位于总进度和筛选栏之间。
2. 取消确认后，成就状态、成就墙数字和通知队列均不变。
3. 确认后只有 `achievement_state` 归零；最高分、收藏、设置、各游戏数据逐项保持原值。
4. 重置后的下一场扫雷使用新的 `sessionId` 与 `eventId` 正常触发首次成就和顶部落款；同一成就再次完成仍不重复弹出。
5. 连续点击、存储失败、离开成就页或应用生命周期中断时，不出现部分清空、旧通知回放或 UI 与存档不一致。
6. 单元测试覆盖规范空状态、通知数据中的空图路径和注册表校验；真机验证确认 Sheet、成功 / 失败反馈与数据边界。

## 6. 验收与风险控制

### 6.1 真机验收清单

- 首页成就 Tab 在浅色、深色、小屏和手机画布模式下，标题、筛选、徽章、进度条、状态日期均不截断。
- 三个筛选状态能切换，空态可读，点击条目能打开和关闭详情 Sheet。
- 成就落款始终只有“一个印记 + 一行文字”：没有游戏 Logo、第二枚徽章、说明文字、漂浮粒子或大面积金色背景；浅色和深色下均有足够文字对比。
- 2048 合成、俄罗斯方块消行、扫雷点击、FreeCell 拖动、Suika 物理帧和 RPS Canvas 运行时，成就落款不吞手势。
- 游戏自身的合成 / 消行 / 结算动画先完成，再出现对应成就提醒。
- 连续解锁按 FIFO 展示；第 4 条后按规则汇总；重复事件、已解锁成就和非正式事件不再提示。
- 进入游戏身份胶囊与成就落款绝不重叠；离开确认、玩法说明等阻断层打开时，队列能够暂停。
- 所有计时器在重开、退出、切换游戏和应用离开时清理，不在回到大厅后突然出现旧通知。
- 用独立开发预览数据连续播放两条普通、单条高光和一条汇总落款；确认预览不会写入 `achievement_state`，也不会影响正式去重测试。
- 用 DEV 清除入口重置后，再完成一次真实扫雷局；确认“清除 → 首次解锁 → 不重复解锁”完整链路与存档边界均正确。

### 6.2 性能边界

- 通知最多包含一个胶囊、一个小印记和一条文字；不加载游戏 Logo、不生成粒子。当前没有勋章 PNG 时显示占位符；填入图路径后才按需加载一张 `28vp` 图片。
- 不使用逐帧 ArkUI 定时器做常驻动画；优先由系统属性动画完成入场、停留和离场。
- 不在 Canvas 渲染循环中判断成就；只在明确的结算 / 高光事件发生时上报事实。
- `backdropBlur` 只能在真机视觉可读、性能稳定后启用；它不是达成新设计的前置条件。
- 不预加载 22 张独立插画；正式勋章资源在列表、详情与落款中均按需使用同一张图，落款仍只占一个小印记位。

## 7. 实施顺序

1. 已完成独立成就核心、真实成就墙、通用队列与扫雷结算事实上报；扫雷以外的游戏仍未接入。
2. 已完成 `AchievementTheme.ets`、`CoopMotion.ets`、`AchievementUnlockNotice.ets` 的胶囊化视觉改造；未改任何 `games/**` 文件。
3. 已完成成就墙 → `HubPage` → `Index` → `AchievementService` / `CoopStorage` 的 DEV 重置链路；入口按当前约定常驻。
4. 勋章 PNG 完成后，将文件放入 `rawfile/app/achievements/` 并填入注册表路径；不把通知重新做成大卡片。
5. 真机确认新落款不挡输入、不与 `GameEntryBadge` 或结果层抢视觉；如有必要再单独评估极轻 `backdropBlur`。
6. 后续按相同的追加式边界逐款接入游戏事实上报。

这样可先保证“判定正确、不会重复、提示不会侵入游戏”，再把视觉从临时占位升级为稳定的轻量反馈。
