# 成就界面与游戏内提醒鸿蒙原生设计

日期：2026-08-26
状态：通用提醒底座已实现；尚未接入任何游戏的事实上报，勋章图片待补

关联文档：

- [成就系统统一设计方案](成就系统统一设计方案.md)：定义成就数据、判定、存档和游戏接入契约。
- [成就墙与解锁反馈体验设计](成就墙与解锁反馈体验设计.md)：定义首期六款游戏的成就内容、触发事实与产品范围。

本文只回答两个体验问题：大厅里的成就界面具体长什么样，以及玩家在游戏中达成成就时，如何以 HarmonyOS 原生方式得到清晰但不打断操作的提醒。

实现状态（2026-08-26）：成就墙已读取独立真实状态；顶部“鸡窝勋章”的展示数据转换、ArkUI 组件、根层内存队列与计时器清理已落地。当前没有游戏上报事件，因此不会在实际游玩中自动弹出；后续只需在选定游戏的安全时机报告事实，不需要在游戏页实现通知 UI。

## 1. 方案结论

成就体验分为两个互相配合的界面：

1. 大厅“成就墙”：像一本轻量的勋章收集册，用于浏览、筛选、查看进度与回顾历史。
2. 游戏内“鸡窝勋章”：顶部居中的非阻断提示，用于告诉玩家“刚刚完成了什么”，不会暂停、不会要求点击确认，也不会吞掉触摸输入。

首版不使用全屏庆祝页、系统 Toast、居中 `CustomDialog` 或底部 Sheet 作为解锁通知。它们分别会打断游戏、无法承载游戏 Logo 与徽章、或遮住操作区。详情 Sheet 只在玩家主动点击成就条目时使用。

```text
大厅：看收藏和进度                    游戏中：只给短暂、明确的高光反馈
┌──────────────────────┐             ┌──────────────────────────┐
│ 成就墙          8 / 22│             │ [Logo]  [徽章]  新成就   │
│ ━━━━━━━━━━━░░░░       │             │              西瓜到手   │
│ [全部][已解锁][进行中] │             │          合成了西瓜     │
│ 合集里程碑             │             └──────────────────────────┘
│ 游戏分组与勋章条目     │                 2 秒后自动淡出，不拦截操作
└──────────────────────┘
```

## 2. 成就墙：页面视觉设计

### 2.1 页面气质

成就页延续鸡窝游戏现有的奶油、纸张、轻玻璃质感，但视觉主题从普通“设置列表”切到“收集到的小勋章”。重点是温暖、清楚、可扫读，而不是堆叠大量金色卡片或做一张新的营销横幅。

- 合集成就使用鸡蛋黄、羽毛绿、木板棕作为共同身份。
- 每款游戏使用其 `GameRegistry` 中已有的 Logo 与主题色，只在局部点缀，不给整页铺满高饱和颜色。
- 已解锁像“收进册子的勋章”：暖金高光、清晰勾选和日期。
- 未解锁不是灰掉的问号：保留名称和条件，让玩家知道下一步可以追求什么。
- 有进度时优先显示细进度条和 `当前 / 目标`，不使用大号百分比抢走游戏内容。

### 2.3 尺寸、层级与交互

| 区域 | 设计规格 | 交互 |
| --- | --- | --- |
| 页边距 | 与大厅一致，左右 `20vp`；组间距 `18–20vp` | 页面在现有 `Scroll` 内滚动，底部留出 Tab 安全空间。 |
| 标题区 | 标题 `22vp`，副标题 `12–13vp`，右侧只显示 `已解锁 X / Y` | 不做跳转，不增加 Banner。 |
| 总进度 | `4–6vp` 高的细条，已完成部分用暖金色 | 只表达总体收集感，不显示夸张百分比。 |
| 筛选器 | 高 `34–38vp` 的三段胶囊，默认“全部” | 点击切换“全部 / 已解锁 / 进行中”，列表以轻微淡入、上移切换。 |
| 分组标题 | Logo `28vp` + 游戏名 + 右侧 `X / Y` | 仅作分组身份；首版不需要折叠，减少额外状态。 |
| 成就条目 | 高约 `72–84vp`，圆角 `16–18vp`，一行一张轻卡片 | 点击打开详情 Sheet，不在条目上放多个小按钮。 |
| 徽章格 | `48vp × 48vp`，圆角 `14–16vp` | 图标与游戏 Logo 共同表意，不能只依赖颜色。 |

每条成就严格保持三栏：左侧徽章、中间标题与条件 / 进度、右侧状态。这样在文字变长、深色模式、系统字体稍放大时，信息仍能稳定排布。

```text
┌─────────────────────────────────────────┐
│ [48 徽章]  成就标题                  已解锁 │
│             条件或简短事实说明    2026-08-24│
│             6 / 10  ━━━━━━━━━░░░         │
└─────────────────────────────────────────┘
```

规则：

- 已解锁的右侧优先显示“已解锁”，日期放在次级文字；没有日期的成就不能伪造日期。
- 未解锁但可量化的条目显示 `6 / 10` 和细进度；一次性条件显示“未达成”。
- 条件文字最多两行，超出时省略，不允许把徽章或右侧状态挤出屏幕。
- “进行中”筛选包含未解锁条目；即使当前没有数值进度，也展示可读条件。
- “已解锁”筛选为空时显示一个轻量空态：“再玩一局，把第一枚勋章带回鸡窝。”不显示空白大插画。

### 2.4 徽章图标语言

首版不需要为 22 条成就各画一张位图插画。建议实现一个可复用的 `AchievementBadge`：游戏 Logo 表示“来自哪里”，语义符号表示“为什么解锁”。

| 语义 | 图标方向 | 适用示例 |
| --- | --- | --- |
| 开始 / 首次 | 星星、鸡蛋、小屋 | 鸡窝开张、初入战场、首次排雷成功 |
| 胜利 / 完成 | 勾选、皇冠、奖章 | 四花归位、平安出窝 |
| 技巧 | 闪电、四格、连线 | 第一记四消、转化风暴 |
| 时间 / 效率 | 时钟、羽毛 | 疾速清台、迅捷排雷 |
| 收集 / 里程碑 | 爱心、收藏夹、六角星 | 常玩收藏、六边形鸡仔 |
| 关键高光 | 金色西瓜、冠星 | 2048 达成、最终合成 |

- 正式素材优先使用 ArkUI `SymbolGlyph` 或项目统一的矢量 / 位图资源；当前没有勋章图片时，提醒内暂用注册表的 `placeholderSymbol` 占位。后续只替换提醒组件内的勋章内容，不让游戏页持有图片或图标逻辑。
- 游戏主题色从 `GameRegistry` 的 `accent` 取得，使用低透明度底色；重要状态才用暖金色加强，不让所有徽章都像稀有奖励。
- 候选 token 集中到 `design/AchievementTheme.ets`，例如 `gold`、`goldSoft`、`lockedSurface`、`lockedInk`、`progressTrack`，不能继续在 `HubPage.ets` 散落色值。
- 深色模式降低背景亮度、保留金色和文字对比；不能仅通过降低整体透明度让锁定文字失读。

### 2.5 成就详情 Sheet

点击单条成就后，使用底部半模态详情，而不是跳转新页。它是玩家主动发起的浏览动作，因此可以使用 `bindSheet` 或自定义详情弹窗。

```text
┌──────────────────────────────────────┐
│                ━━━━━                  │
│             [大号成就徽章]             │
│              西瓜到手                  │
│       在鸡窝水果摊首次合成西瓜           │
│                                      │
│  当前状态   已解锁                      │
│  解锁时间   2026-08-24 14:30            │
│  来源游戏   鸡窝水果摊                  │
│                                      │
│              [ 知道了 ]                │
└──────────────────────────────────────┘
```

未解锁时把“解锁时间”替换为“达成条件”或“当前进度”。详情中不加入分享、领奖、货币、广告或任务跳转；首期的成就是纯收集与回顾。

## 3. 游戏内提醒：顶部“鸡窝勋章”

### 3.1 位置与外观

“鸡窝勋章”固定在顶部安全视觉区，水平居中。它是悬浮信息，不是游戏 UI 的新常驻控件。

```text
┌──────────────────── 手机屏幕 ────────────────────┐
│ 系统安全区                                         │
│                                                    │
│          ┌──────────────────────────┐              │
│          │ [Logo] [金徽章]  新成就   │              │
│          │               西瓜到手   │              │
│          │             合成了西瓜   │              │
│          └──────────────────────────┘              │
│                 游戏顶部栏 / HUD                    │
│                                                    │
│                 棋盘 / Canvas / 操作区             │
│                                                    │
│                 底部按键或系统手势区               │
└────────────────────────────────────────────────────┘
```

| 项目 | 规格 |
| --- | --- |
| 位置 | 顶部居中；当前实现固定为 `top: 24vp`，与 `GameEntryBadge` 同一安全视觉区。首个游戏接入时若顶部栏确实冲突，再通过游戏壳增加 `noticeTopInset`，而不是让游戏页各自写浮层。 |
| 尺寸 | 当前固定 `276vp × 70vp`，处于设计区间 `240–280vp × 64–72vp` 内；小屏优先收窄宽度，不放大高度。 |
| 内容 | 游戏 Logo、金色徽章、“新成就”、成就名称、最多一条短事实说明。 |
| 背景 | 奶油半透明面板 + 细描边 + 轻阴影；深色模式换为深暖灰面板。 |
| 输入 | 完全不响应点击和手势，使用 `HitTestMode.None`。 |
| 层级 | 只在游戏可见时显示，位于游戏场景之上；与进入身份胶囊、退出确认等高优先级状态做队列避让。 |

`noticeTopInset` 不应在每个游戏里硬编码一套浮层；应作为游戏壳的展示配置或回调提供给 `Index.ets`。当前项目已经使用 `CoopViewport` 管理手机画布尺寸，通知也应以该画布为参照，而不是在宽屏上直接用全窗口绝对坐标。

### 3.2 三种展示等级

| 类型 | 场景 | 外观与时长 |
| --- | --- | --- |
| 普通勋章 | 首局、普通胜利、累计局数 | 轻微下落 + 徽章弹性；总计约 `2.5s`。 |
| 高光勋章 | 合成 2048、第一记四消、合成西瓜、最终合成 | 普通样式基础上增加 2–3 枚低成本星点 / 羽毛粒子；总计约 `3.0s`。 |
| 汇总勋章 | 同一次事实上报解锁超过 3 条 | 显示“本局新解锁 X 项成就”，约 `2.5s`；详情留在结算页和成就墙。 |

动效节奏：

1. `180ms`：从上方 `8–12vp` 下落并淡入，徽章缩放一次。
2. `2.1s`（高光可 `2.6s`）：稳定可读，不持续播放粒子。
3. `220ms`：向上 `6–8vp` 淡出。

避免对宽高、列表布局或棋盘状态做动画。只使用 `opacity`、`translate`、`scale` 等图形变换，减少布局重算和游戏帧率压力。

### 3.3 何时提醒才不打断游戏

原则是：**成就可以立即判定和保存，但视觉提示一定排在游戏自身高光之后。**

| 游戏 | 成就 | 安全展示时机 |
| --- | --- | --- |
| `rpsBattle` | 首局、支持阵营获胜、转化风暴 | 结果层已经稳定约 `350ms` 后。 |
| `freecell` | 通关、少步、限时 | 胜利结果层出现后。 |
| `minesweeper` | 胜利、快速、插旗 | 胜利结果层出现后。 |
| `chicken2048` | 256、1024、2048 | 合成动画、分数变化和棋盘状态稳定后；不能在手势滑动中插入。 |
| `tetris` | 第一记四消 | 消行动画完成、落块稳定后；其他结算型成就在结算层后。 |
| `suika` | 西瓜、最终合成 | 合成和物理反馈结束后；普通分数类在结算后。 |

以下时机一律延后：

- 游戏刚进入时的 `GameEntryBadge` 仍在显示。
- 暂停、玩法说明、离开确认、失败确认等阻断型覆盖层正在显示。
- 页面正在切入 / 切出，或当前游戏已经离开。
- 同一局的前一条成就通知尚未结束。

结算页还应有一个“本局新成就”小区域。它让玩家在顶部提示自动消失后，仍能看清本局获得了哪些勋章；不需要再次播放通知。

### 3.4 队列与提示边界

```text
游戏事实上报
  -> 成就引擎返回 newlyUnlocked
  -> 立即存档（解锁状态不会丢）
  -> 进入内存通知队列
  -> 等待可展示时机
  -> 展示一条鸡窝勋章
  -> 自动淡出并展示下一条 / 汇总条
```

- 当前一批 `newlyUnlocked` 最多逐条展示 3 条；第 4 条及之后合并为一条汇总通知。第一款游戏接入时，再结合其 `sessionId` 验证跨多次上报的同局合并时机。
- **严格串行：** `Index.ets` 以 FIFO 入队；前一张通知完成出场、卸载后才允许下一张挂载。两条或三条成就不能并排、叠放或同时播放。首局扫雷若同时解锁“鸡窝开张”和“平安出窝”，按引擎返回顺序依次完整播放。
- 重复 `eventId`、调试局、已解锁成就都不会从成就引擎返回为 `newlyUnlocked`，因此不会进入队列。
- 队列只保存在内存中；应用被关闭时不补播旧提示，持久化的只有成就进度与解锁时间。
- 解锁音效和轻震动只在现有全局设置真正启用时播放，且仅首次解锁时触发；首版不强行新增音效。
- 通知不做点击跳转，避免 `HitTestMode.None` 与游戏拖拽、滑动、按键发生冲突。

当前根层队列会避开 `GameEntryBadge`、场景转场、返回大厅和退出 / 页面销毁；阻断型游戏覆盖层的精确等待时机由后续每款游戏在“玩法反馈已稳定”后再上报事件来保证。这样不会为了提示组件提前改动任何游戏。

队列顺序的纯逻辑由 `AchievementNotice.test.ets` 覆盖；真机接入时还必须观察连续两条卡片无视觉重叠、无输入拦截。

## 4. HarmonyOS 原生实现选型

### 4.1 推荐方案：`Index.ets` 根 `Stack` 的声明式浮层

本项目最合适的首版方案是把 `AchievementUnlockNotice` 挂在 [Index.ets](../../entry/src/main/ets/pages/Index.ets) 的根 `Stack`，由 `Index.ets` 统一维护通知队列和显示状态。

理由：

- `Index.ets` 已经是所有游戏的共同路由、存档入口，并且已有根级 [GameEntryBadge.ets](../../entry/src/main/ets/shell/GameEntryBadge.ets)。
- `GameEntryBadge` 已经验证了顶部居中、`opacity + translate`、计时器清理和 `HitTestMode.None` 这条实现路径；成就通知可以复用同样的可靠边界。
- 成就判定、存档、队列和 UI 只需要一个所有权，不会让六个游戏各自维护 Toast、计时器和重复逻辑。
- 当前是单 `Index` 编排的应用，不需要为了一个小胶囊过早引入更复杂的全局 Overlay 生命周期。

建议的根层级：

```text
Index 根 Stack
  ├─ GameSceneTransition（大厅或当前游戏）
  ├─ GameEntryBadge（短暂的进入身份胶囊）
  └─ AchievementUnlockNotice（短暂的鸡窝勋章）
```

`GameEntryBadge` 与 `AchievementUnlockNotice` 不同时展示。通知队列在前者卸载后才开始播放。阻断型覆盖层的等待不在当前无游戏接入阶段猜测；首个游戏接入时只在它自己的结果层或高光反馈稳定后上报事实。

### 4.2 为什么不直接用 Toast 或 Dialog

HarmonyOS 官方的弹窗选型中，Toast 面向简单即时反馈，`OverlayManager` 面向完全自定义的浮层 / 胶囊，而 `bindSheet` 与 Dialog 适合覆盖旧界面的交互内容。[ArkUI 弹窗概述](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/arkts-dialog-overview)

| 方案 | 是否用于游戏内解锁 | 原因 |
| --- | --- | --- |
| 根 `Stack` 声明式浮层 | **首版采用** | 与现有 `Index.ets` 状态流和 `GameEntryBadge` 完全一致，样式、队列、深浅色和触摸可控。 |
| `OverlayManager` | 后续备选 | 官方适合高度自定义的浮层胶囊；若项目以后切换到多页面 `Navigation`，可将通知协调器迁移过去。 |
| `promptAction.showToast` | 不采用 | 适合简单文字反馈，难以稳定承载游戏 Logo、徽章、队列、与进入胶囊的避让及本项目视觉。 |
| `CustomDialog` | 不采用 | 是模态交互，可能拦截系统返回和游戏触摸，不适合“玩着玩着”的提示。 |
| `bindSheet` | 只用于详情 | 玩家主动点击成就时查看完整条件、进度与解锁时间。 |

### 4.3 动画和触摸的原生做法

- 组件插入 / 移除优先使用 `transition`；鸡窝勋章内部的短缩放、透明度和位移使用 `UIContext.animateTo` 或组件 `.animation()`。
- 华为的 ArkUI 动画指南建议使用系统动画能力，并尽量用 `opacity`、`translate`、`scale` 等图形变换，而不是频繁修改布局属性；这正适合短暂提示。[ArkUI 动画使用指南](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-animation-usage-guide)
- 通知外层设置 `.hitTestBehavior(HitTestMode.None)`。官方的触摸测试控制支持通过该模式使浮层不参与自身触摸响应，从而不抢走棋盘点击、拖拽和底部按键。[触摸测试控制参考](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/ts-universal-attributes-hit-test-behavior)
- 仅在入场 / 出场更新小而稳定的状态字段，Canvas 游戏的实体数组、物理状态和 ArkUI 页面状态不要因通知而每帧刷新。

### 4.4 建议文件边界

| 文件 | 职责 |
| --- | --- |
| `shell/AchievementModule.ets` | 成就、进度、结算结果、即时事件和通知数据类型。 |
| `shell/AchievementRegistry.ets` | 静态成就目录、标题、图标语义、游戏归属、展示等级。 |
| `shell/AchievementEngine.ets` | 纯判定：输入独立成就状态与玩法事实，输出新进度和 `newlyUnlocked`。 |
| `shell/AchievementNotice.ets` | 纯展示数据转换：过滤无效项、生成单条通知，并在一批解锁超过 3 条时生成汇总通知。 |
| `design/AchievementTheme.ets` / `design/CoopMotion.ets` | 通知的尺寸、颜色与动画时长 token，避免在组件或游戏页散落常量。 |
| `components/AchievementUnlockNotice.ets` | 顶部非阻断鸡窝勋章，只消费展示数据。 |
| `pages/AchievementWall.ets` | 成就墙、筛选和分组列表；不写玩法阈值。 |
| `pages/Index.ets` | 唯一的队列所有者：接收事件结果、协调通知与进入胶囊，并在离开时清理计时器。 |

## 5. 状态流和接口约束

### 5.1 游戏页只报告事实

当前游戏页主要回调 `recordScore(score)`。成就接入时逐步升级为结算结果与可选即时里程碑：

```text
正常结算：recordGameResult(GameSessionResult)
高光瞬间：reportAchievementEvent(GameAchievementEvent)
```

例如：

- 2048 在合成时报告 `maxTile`，引擎决定是否首次达到 256 / 1024 / 2048。
- 俄罗斯方块在结算时报告 `lines`、`level`，在四消完成后可报告一次高光事实。
- 水果摊在合成反馈完成后报告 `mergeLevel` 或 `isFinalMerge`。
- 游戏不得直接写某个成就 ID、直接显示勋章、直接访问 `preferences`。

### 5.2 `Index.ets` 的通知协调职责

`Index.ets` 新增的状态应保持小且稳定：当前通知、是否已挂载 / 可见、内存队列和少量计时器。做法应参考现有 `showEntryBadge()`、`hideEntryBadge()` 与 `clearEntryBadgeTimers()`，并在 `aboutToDisappear()` 中清理所有成就通知计时器。

建议的执行顺序：

1. 收到结算或即时事件，先让 `AchievementEngine` 判定。
2. `AchievementService` 先保存独立的成就状态与已解锁时间；游戏记录仍沿用原有路径，两者不互相推导。
3. 仅把本次真正新解锁且可提示的条目加入内存队列。
4. 若进入胶囊、场景转场、返回大厅或已有通知正在显示，则等待；游戏自己的阻断覆盖层应在稳定后才上报事实。
5. 展示结束后清理当前通知，再处理下一条或汇总条。

通知组件只读取 `AchievementNoticeItem`，其中有 `achievementIds`、`gameId`、标题、短说明、占位符号和展示等级。它不能二次判定或读写存档。

## 6. 验收与风险控制

### 6.1 真机验收清单

- 首页成就 Tab 在浅色、深色、小屏和手机画布模式下，标题、筛选、徽章、进度条、状态日期均不截断。
- 三个筛选状态能切换，空态可读，点击条目能打开和关闭详情 Sheet。
- 2048 合成、俄罗斯方块消行、扫雷点击、FreeCell 拖动、Suika 物理帧和 RPS Canvas 运行时，鸡窝勋章不吞手势。
- 游戏自身的合成 / 消行 / 结算动画先完成，再出现对应成就提醒。
- 连续解锁按队列展示；第 4 条后按规则汇总；重复事件、迁移补发和调试局不再提示。
- 进入游戏身份胶囊与鸡窝勋章绝不重叠；离开确认、玩法说明等阻断层打开时，队列能够暂停。
- 所有计时器在重开、退出、切换游戏和应用离开时清理，不在回到大厅后突然出现旧通知。

### 6.2 性能边界

- 通知最多包含一个主面板、一个 Logo、一个徽章和不超过 3 个短生命周期粒子。
- 不使用逐帧 ArkUI 定时器做常驻动画；优先由系统属性动画完成入场、停留和离场。
- 不在 Canvas 渲染循环中判断成就；只在明确的结算 / 高光事件发生时上报事实。
- 不预加载 22 张独立插画；Logo 复用现有游戏资源，徽章以系统符号 / 统一资源组合实现。

## 7. 实施顺序

1. 已完成独立核心、真实成就墙和本页约定的通用提醒底座；没有修改 `games/**`。
2. 由产品负责人指定第一款游戏，并确认一个明确的结算或里程碑事实上报位置。
3. 只在该游戏的安全时机接入通用 `reportAchievementEvent`，补该游戏的规则 / 时机测试。
4. 真机确认通知不挡输入、不会和游戏自身高光或 `GameEntryBadge` 重叠。
5. 按同样的边界逐款接入其余游戏；勋章 PNG 完成后只替换通用组件的中心素材。

这样可先保证“判定正确、不会重复、提示不会侵入游戏”，再逐步完成每款游戏的真实时机验收。
