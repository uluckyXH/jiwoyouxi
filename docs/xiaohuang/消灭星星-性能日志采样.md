# 消灭星星 · 重进与性能日志

日期：2026-09-19。日志标签为 `StarPopPerf`，当前格式为 `v3`。用于用户设备反馈，不把主机测试耗时当成设备性能。

## 怎样提供一段有用的日志

在 DevEco 的 HiLog 中选中当前 App 进程，日志等级包含 Info，筛选 `StarPopPerf`。先开始采集，再执行下面的操作，复制这一段完整日志即可。

1. 从首页进入消灭星星，连续消除几组，包含一次较大的组和一次空列左靠。
2. 保存并退出，再重新进入，确认没有“摆一盘新的星星”弹窗闪现。
3. 如果卡顿出现在展开/收起、切换主题、下一关或撤销时，把对应动作也录入同一段日志。
4. 出现卡顿后稍等一秒再复制；带上进入、操作、退出的前后文，比只截一条峰值更容易定位。

可附上设备型号和当时的屏幕形态，以及卡顿是在按下、消除、下落、左靠还是重新进入时。无需清空存档或重装 App 来采集。

## 本次修复

原先页面的默认弹窗和读档开始状态都是 `loading`，快速恢复存档也会先创建遮罩，再立即关闭。现在普通进入和恢复都不创建加载弹窗；等待超过 300ms 才在棋盘提示区显示一行准备文字，读取结束即清理。读取失败、损坏存档、真实结算仍有明确面板。

退出意图会立即使未完成的读取和生成结果失效，不再等页面销毁才拦截。首次生成被后台打断时，不把构造时的备用棋盘误当成新局保存；返回后继续准备。

## 日志内容

每条日志都有本次访问编号和进入后的相对毫秒数，可区分反复退出重进。

| 记录 | 主要用途 |
| --- | --- |
| 进入页面、读取存档、恢复校验、进入完成 | 分开查看磁盘读取、数据校验和状态提交；说明来源是存档还是新局、关卡及最终弹窗 |
| 弹窗变化、后台暂停、返回大厅、页面释放 | 对齐用户看到的面板，区分窗口隐藏和失去活跃状态；确认退出清理 |
| 生成棋盘 | 记录总等待、切片数、计算合计、最慢切片、验证耗时、取消及备用方案 |
| 消除、棋盘状态提交、按下预览、提示计算及提交 | v3 分开记录规则、状态、存档入队、音效提交、位移准备及 animateTo 提交；记录组大小、剩余块数和是否左靠 |
| 下落提交、左靠提交 | 阶段同步提交达到 8ms 时记录耗时和实际移动节点数 |
| 动画调度延迟 | 动画阶段计时器实际等待超过计划至少 12ms 时记录；用于寻找主线程调度停顿 |
| 布局 | 记录真实窗口、连续可用区域、格子尺寸、侧栏、折痕数量、小窗状态及计算/提交耗时 |
| 保存链路、写入存档、成就上报 | 区分排队与成就确认造成的总等待、单次存档写入及成就上报等待 |
| 输入拦截 | 记录动画锁定、保存、尚未读入、弹窗等拦截原因；首次和每十次输出 |
| 短帧采样 | 记录首个回调等待、回调间隔 P95、最长间隔及超过 34ms 的次数 |

## 采样开销与解释边界

- 计时使用系统单调时钟，输出毫秒小数；包含线程被抢占的等待，不等于纯 CPU 执行时间。
- 仅在进入、恢复、有效消除、撤销、下一盘、主题变化和窗口重排时启动短帧采样。通常 600ms，首次进入 800ms；后续动作替换旧采样。后台或退出立即停止。
- 使用 DisplaySync 请求 60Hz 回调，回调里只累计数字，最多保留 120 个间隔；不逐帧写日志，也不驱动棋盘渲染。不支持时只输出不可用，绝不另起循环定时器模拟帧率。
- 帧回调间隔反映回调调度，**不是 GPU 实际呈现帧率**。采样本身也有少量开销，若规则和调度正常但视觉仍卡顿，再用设备工具查布局、SVG 解码和 GPU；不会凭当前日志声称已经证明 GPU 性能正常。
- 正常保存只记首次与每十次；总等待达到 100ms 或失败则立即记录。单次存档写入/成就上报达到 32ms 或失败才单独记录。预览/状态提交达到 8ms 才单独记录。
- 不打印完整存档、完整棋盘或账户资料。不添加 UI 调试浮层，不改变分数、成就与玩法规则。

代码与清理行为的验证见 [本次验证报告](../../测试报告/2026-09-19-消灭星星重进与性能日志.md)。实际触控、动画观感及设备负载等待用户反馈。

## 根据 17:27–17:28 的设备日志做的第一轮优化

这段 v2 日志中，消除规则为 3.53–5.16ms，单次同步提交为 158.91–249.72ms；随后的帧回调间隔出现 136–267ms 峰值。开局生成的验证部分为 43.35ms。它们说明主要停顿发生在规则之外；保存等待同时覆盖这段时间，不能单凭异步等待值认定存储设备慢。

已经改为稳定棋子对象加独立原生棋子组件，每个 UI 属性由 `@Track` 单独观察。选择、缩小、隐藏和移动只修改实际变化的棋子字段，绘制中不再对共享棋盘数组反复 `find`/`includes`。80 个节点在当前关卡内复用，撤销恢复原节点；难度或关卡改变才重建该关模型。棋盘禁用放在容器，避免每一颗都切换禁用状态；移除棋子内部多余的 Stack/选中覆盖节点。

开局验证直接寻找证据落点的连通组，不再每一步重新枚举全盘所有组；全盘找组复用访问标记，位移准备改用按 ID 索引。目标、证据、分数、存档格式和成就规则不变。

`同步提交`是整个输入处理区间，**包含 animateTo 为动画准备而同步执行的 UI 刷新**。v2 的“不含后续布局”不足以表达这段平台工作，因此 v3 专门列出动画提交耗时；它仍然不是 GPU 呈现耗时。保存、成就提交仍按原顺序执行，没有以丢弃保存来换取流畅。

再次采集时确认日志出现 `[消除 v3]`，对比 `同步提交`、`动画提交`、`下落提交`、`左靠提交`与`最长`间隔。设备上的实际降幅需这次运行的数据验证。

属性级观察采用 SDK 支持的 [OpenHarmony @Track 用法](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/state-management/arkts-track.md)；所有在棋子 UI 中读取的模型字段均已标记，避免混用未追踪字段。第一轮验证见 [性能优化报告](../../测试报告/2026-09-19-消灭星星增量更新优化.md)。
