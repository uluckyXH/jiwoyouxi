# 水果摊：半折叠与小窗口处理

日期：2026-09-18。范围为新版 `gamesNext/fruitMarket`。保留已验证的 v4 物理和绘制算法。

## 检查结果

原实现已经监听系统折叠状态：在 `FOLD_STATUS_HALF_FOLDED` 时读取首条折痕，将屏幕像素坐标转换为窗口内 vp 坐标。布局避开状态栏、导航区、挖孔和折痕，选择上下或左右较大的连续区域。展开、收起与旋转只改变布局，不创建新的物理世界。

原实现缺少最小可玩区域兜底。例如 390×844vp、横向折痕位于 y=412、厚 20vp，扣除顶部 24/bottom 20vp 安全区后，选择下半边 390×392vp，摊位只有约 115×166vp。继续缩放会让水果与落点太小。

## 本次行为

- **区域足够**：沿用原来的手机纵向布局或大屏侧栏布局；半折叠只要一侧足够大，也能继续使用。
- **区域过小**：切换为浅深色适配的引导卡片，提示展开屏幕或放大窗口。使用原创 SVG 展开图标；卡片可以滚动，保留返回大厅入口。
- **保护对局**：停止刷新调度、取消进行中的触摸、停止声音并尝试保存；不推进物理、越线倒计时或投放冷却，也不接受隐藏画布的迟到触摸事件。
- **恢复空间**：保留同一局，显示“继续摆摊”，由用户主动恢复。原本处于玩法、暂停、重开确认、存档恢复或结算页时保留原页面状态。
- **返回大厅**：优先保存；失败时仍留在提示页并可重试，也保留用户主动选择不保存返回。系统返回键不会打开一个被提示卡遮住的确认框。
- **折痕边界**：只有折痕与当前窗口实际相交、且横跨可用区域时才切分。其他窗口区域内的折痕不会误触发小区域提示。

## 判定口径

按安全区和折痕处理后的实际 vp 尺寸判断，不通过手机、折叠屏或平板机型名称拦截。

任一条件成立才显示提示：

1. 可用区域宽度小于 280vp，或高度小于 260vp；
2. 纵向布局最终摊位宽度小于 140vp；
3. 由半折叠折痕分出的区域，最终摊位宽度小于 180vp。

第 3 项只用于已经被折痕分开的区域，不套用到正常手机横屏。布局检查覆盖 320×480、320×568、390×844、568×320、844×390、768×1024、1024×768、1280×800 和 720×720vp，均保持可玩状态。

| 例子（安全区顶部 24 / 底部 20vp） | 结果 |
| --- | --- |
| 普通手机 390×844 | 正常纵向布局，摊位约 366×529vp |
| 小手机 320×480 / 320×568 | 正常可玩 |
| 手机横屏 568×320 / 844×390 | 保留现有横屏布局 |
| 390×844 横向半折叠 | 选取 390×392vp 下半区，显示展开提示 |
| 840×1000 横向半折叠 | 选取较大一侧，摊位约 234×338vp，可继续玩 |
| 展开的大屏 1000×840，竖向折痕后单侧约 480/500vp | 区域足够，保持可玩 |
| 很小的外屏或窗口 344×368 | 显示展开屏幕或放大窗口提示 |
| 平板 1024×768 | 正常侧栏布局 |

阈值用于避免不可操作的小画布，不表示上述逻辑检查替代了对应硬件的视觉验收。

## 验证

- 23 组纯逻辑检查通过，新增小区域判断、正常手机不误拦截、折痕不相交与部分相交；原合成、保存、满筐物理和布局检查仍通过。
- 4 组页面生命周期检查通过：使用实际页面方法，替换原生 UI/存储适配器，验证折叠时取消拖动、暂停并保留对局；阻止迟到回调/触摸；展开后手动继续；保留各类弹窗；加载期间折叠；小窗口保存失败与系统返回。
- 原有 6 组绘制与 3 组刷新调度检查通过。v4 的日志检查代码未更改。
- 应用和原生测试包编译通过。未自动切换用户模拟器；折叠真机上的系统事件、卡片视觉、滚动与触摸仍需设备确认。

当前系统接入仍是已有的单条半折叠折痕路径。多铰链设备的组合折叠状态与多条折痕尚未专项验收；完整展开时仍按实际窗口尺寸布局。
