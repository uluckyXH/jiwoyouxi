# 水果摊尺寸与性能跟进（v4）

日期：2026-09-18。代码范围为 `gamesNext/fruitMarket`，旧版水果游戏的实现、素材和存档不变。

## 日志说明了什么

| 实测场景 | 用户提供的原生数据 | 判断 |
| --- | --- | --- |
| PX-v2，15–17 颗水果 | 回调约 13.6–16.9 FPS，物理平均约 49–64ms；451px 离屏纹理返回 1578.5px 位图，差 3.5 倍 | 离屏缓存存在设备密度偏差；物理补算负担过重 |
| v3，9–16 颗水果活动中 | 多数回调约 60–64 FPS，活动物理平均约 4.6–8.7ms | 少量水果时已有改善，不能代表满筐性能 |
| v3，31 颗水果活动中 | 回调 17.9 FPS，物理平均 46.553ms，每回调补 2 步，配对约 1473.5 次 | 密集堆叠仍然耗时，补算进一步加重负担 |
| v3，36 颗水果全部休眠 | 求解步与配对为 0，但绘制提交平均仍约 1.7–2.4ms，间隔 P95 约 30–35ms | 每回调仍重复提交整筐 SVG；也存在回调调度或其他渲染成本，不能只看物理平均 |
| v3，35 颗水果重新活动 | 回调 22.6 FPS，活动物理平均 69.383ms，物理峰值 149.575ms | 全局休眠在新投放时唤醒整个果堆，平均值会被休眠回调稀释 |

这些区间耗时包含线程被抢占或等待的时间，不等于纯 CPU 执行耗时。回调 FPS 不是 GPU 呈现帧率，Canvas 提交快也不能证明 GPU 绘制便宜。v3 的休眠日志中也出现过 78ms 的单次“物理”区间，因此新增停顿明细，避免把所有异常都归因于碰撞计算。

## v4 满筐设备反馈（13:44–13:45）

来源：用户运行 v4 后复制的 10 条连续五秒汇总和 1 条停顿明细，说明水果已放得很满，并反馈“感觉比上一版好多了”。[采样记录](性能采样/2026-09-18-v4满筐.txt) 保留原时间与诊断字段，仅省略进程/PID 等列。

| 场景 | 这次 v4 的实测结果 |
| --- | --- |
| 31 颗水果 | 24 颗休眠，回调 59.1 FPS，物理平均 9.441ms，活动物理平均 9.907ms；此前 v3 的 31 果样本为回调 17.9 FPS、物理平均 46.553ms |
| 38 / 41 颗水果 | 分别有 29 / 37 颗休眠，回调 58.1 / 59.9 FPS，活动物理平均 9.464 / 8.180ms |
| 35 果、期间大部分时间休眠 | 319 次回调只重画 52 次，跳过 267 次（83.70%）；绘制提交平均 0.298ms，整次回调平均 2.087ms |
| 最后一个 40 果窗口 | 结束时 40 颗全部休眠；期间回调 62.0 FPS、间隔 P95 18.55ms |
| 全部约 50 秒采样 | 回调 58.1–63.6 FPS；3045 个已记录间隔中 10 个超过 33.4ms，占 0.328%；最长间隔 47.49ms |

这份记录支持局部休眠和按需绘制已在设备上生效，且没有再出现此前满筐时持续约 18–25 次回调/秒的情况。前后来自不同对局，不是相同输入、相同场景的严格 A/B 测试，不把它们用于承诺固定提升比例。

仍有一次需要保留的异常：13:45:38 的物理区间为 43.887ms，总回调 45.439ms；该回调执行了 2 步、12 轮求解和 132 次窄相检查。代码允许每步最多 6 轮，因此这是达到现有补算上限的一次回调。单条区间日志无法进一步分离实际执行时间与线程抢占等待，也不能证明某一个循环就是全部原因。部分窗口 P95 仍约 29–30ms，慢帧统计的阈值是 33.4ms；0.328% 不是 GPU 掉帧率，也不表示其余每次都在 16.7ms 内完成。

**本轮决定：保留 v4 作为当前性能基线，不继续调整碰撞参数、休眠阈值或削减求解轮数。** 当前数据和用户手感均显示主要卡顿已有改善，优先保持堆叠与合成稳定。本轮只归档设备记录、更新判断，没有再次修改游戏算法。已有的限频诊断继续保留；后续若出现可复现的持续卡顿，再依据当时对局与日志定位，必要时补原生呈现/调度采样。用户可以正常试玩，无需现在重复一轮相同压力测试。

## v4 已改内容

1. **逐颗休眠与局部唤醒**：每颗水果稳定 0.8 秒、合成锁解除且存在地面或下方水果支撑后休眠。新投放只让新水果活动；强碰撞、较深穿透或支撑消失会唤醒受影响的水果。远处稳定果堆不必重新积分和求解。
2. **复用近邻接触对**：每个物理步建立一次带余量的候选接触列表，在最多 6 轮求解中复用；水果移动超过安全余量、合成或局部唤醒时重新建立。休眠水果之间不参与碰撞求解，半径与逆质量预先计算。
3. **减少堆叠微动**：位置约束已经阻止向下位移时，限制残留的向下速度，避免重力速度反复唤醒已经稳定的支撑。保留向上反弹。
4. **静止画面按需重画**：果堆全部休眠、合成效果结束且画面状态没有变化时，不再清空 Canvas 或重新提交整筐 SVG。瞄准、投放、主题、尺寸、警戒倒计时、素材加载完成或画布重建都会触发刷新。暂停时切换主题也会刷新。
5. **保存休眠状态**：原有 v1 对局增加可选 `resting` 水果 ID 列表。旧存档仍可读取；恢复时检查 ID、速度、合成锁、边界与支撑，不让无支撑或越界的水果被错误冻结。没有清空或覆盖设备现有对局。
6. **增加可区分的诊断**：仍每 5 秒汇总，新增休眠水果、重画回调、宽相/窄相检查、求解轮、绘制/总回调峰值、存档提交峰值；较长停顿最多每 2 秒额外输出一条明细。记录使用 DisplaySync 还是 Timer 调度。

继续保留 v3 的原始 SVG 直接绘制、60Hz 固定模拟步长、每回调最多补 2 步与超额时间丢弃。没有重新引入离屏位图缓存或针对某个密度的临时放大倍数。源 SVG、布局、触摸和 Canvas 均使用默认 vp，水果图形的圆心与半径直接对应物理碰撞体。

水果级别、合成分数、500ms 投放间隔、音效、主题资源和经典版入口不变。碰撞与休眠策略变化可能改变细微轨迹；不承诺相同操作产生与旧算法逐帧相同的果堆。

## 已验证与仍待实测

- **纯逻辑 21 组**：投放、队列、计分、合成锁、存档、越线、慢回调上限、30/60/120 回调频率一致性、手机/平板/折痕布局；新增局部休眠、支撑合成后的唤醒与继续合成、深度重叠时重建接触列表、安全恢复休眠状态。
- **真实密集几何回放**：只读取得 35 颗水果的对局，提取等级与坐标为匿名测试夹具。主机回放 10 秒后 35 颗全部休眠；新水果自由下落时原 35 颗保持休眠；继续多次投放后位置有限、边界有效且对局可继续。没有把回放状态写回设备。
- **绘制 6 组**：SVG 加载复用与失败兜底、延迟加载恢复、失败释放、11 级水果在 4 种密度与 3 种画布宽度下的几何尺寸、静止时连续 300 次回调不重画；瞄准、主题、尺寸、画布重建、倒计时和投放仍触发刷新。这是主机调用/几何检查，不是原生像素验收。
- **日志 4 组、刷新调度 3 组**：验证聚合、恢复后的统计、活动耗时与休眠分离、无重画计数、峰值、停顿明细及限频。上述共 34 组在主机执行。
- 应用与原生测试包已编译通过；原生测试包编译成功不等于测试已在设备执行。
- 主机持续活动的合成基准没有证明 v4 全面变快：禁止合成和休眠的 24/64/120 颗场景，v3 与 v4 的 Node 耗时接近。设备上的局部休眠和按需绘制收益以上述用户日志为依据，不能把 Node 毫秒数当作鸿蒙设备性能。

设备日志现已由用户提供，包含 18–41 颗水果以及部分/全部休眠状态，见上面的满筐设备反馈。尚未测量 GPU 呈现帧率，因此结论限于这次回调与提交数据，以及用户反馈的手感改善；不宣称所有设备、所有对局均稳定 60 帧。

## 后续复现卡顿时如何复制日志

1. 用 DevEco Studio 的 **Run** 运行最新代码，进入首页新版水果摊，继续现有对局即可。
2. 打开底部 **Log → HiLog**，选择测试设备及 `com.longxin.jiwoyouxi` 进程。
3. 日志级别选 **Info** 或 **All**，搜索或按 Tag 过滤 **FruitMarketPerf**。
4. 确认出现 **`[水果摊 v4 按需绘制]`** 或 **`[开始采样 v4]`**。仍显示 v3/PX-v2 就是旧代码。
5. 到 **30–40 颗水果**时连续投放约 20 秒，再**停手 10–15 秒**，随后继续投几颗。复制这三段的连续 **`[5秒汇总 v4]`**、期间全部 **`[停顿详情 v4]`**；如有 **`[绘制回退]`**也一起复制。顺便说明哪一段手感卡，水果显示大小是否正常。

不需要逐帧抓日志。数值均为公开输出，复制后不会变成 `<private>`。

## 字段怎么看

- `休眠水果`：汇总结束时保持静止的水果数。新投放时它可以小于总数，也不应该无条件归零。
- `重画回调`：这 5 秒里实际提交过画面的回调数。完全停稳、特效结束且不操作时应接近 0；活动中则按需绘制。
- `活动物理平均`：只统计实际积分/求解的回调，避免被大量休眠回调稀释。与物理峰值、P95、慢帧数一起判断。
- `宽相检查`：建立近邻列表时检查的候选；`窄相检查`：求解时检查的接触对。v3 的“配对”统计口径不同，不能直接据此计算 v3→v4 百分比收益。
- `回调外间隙`：本次回调间隔减去上一次已测回调总耗时，只用于定位未覆盖的时间，不能单凭它认定 GPU 或系统调度是原因。
- `存档提交`：本回调内序列化并发起保存的同步部分，不含异步磁盘写入完成时间。
- `绘制提交`与所有峰值：测的是调用区间，不是 GPU 完成时间，也不能排除线程抢占。`总回调`覆盖本次测量中的物理、效果处理、绘制和同步存档提交；统计与日志输出自身不包含在该数值内。
- `回调源`：确认使用 DisplaySync，或使用设备不支持时的 Timer 回退。

诊断不写文件、不更新诊断 UI；`MarketPerformance.ets` 的 `MARKET_PROFILE` 暂时保持开启。
